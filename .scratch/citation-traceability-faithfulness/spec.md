# 引用溯源与忠实性评估

Type: spec
Status: ready-for-agent

## 问题陈述

企业知识库的使用者需要知道一个回答为什么值得信任。当前查询管道能够返回进入模型上下文的文档和 chunk，但无法区分“模型在回答中明确引用的内容”和“仅仅作为上下文提供给模型的内容”。用户因此难以把回答中的某条具体事实准确定位到支撑它的文档位置。

当前回答 Prompt 对引用格式的约束也不够严格，并且没有充分防止模型偷懒概括。参考内容中可能包含五六条必须执行的流程，模型却只回答“按照规定流程操作即可”。这种回答虽然简洁，但缺少实际操作价值，也破坏了企业知识库对制度完整性的要求。

系统目前还缺少在线判断回答是否忠实于参考内容的质量信号。但增加忠实性评估时，不能让质量观测能力成为新的主链路故障点，不能为了修复引用增加不必要的模型调用，不能向用户暴露可能产生误导的自评估分数，也不能削弱现有检索层权限隔离。

## 解决方案

在现有 V4 RAG 查询管道中补齐回答级引用溯源与抽样忠实性评估。

V4 专用回答 Prompt 要求每条事实使用统一引用标记，并要求参考内容中可见的流程、编号、条件和列表按原顺序完整回答。模型完成生成后，系统解析回答中的引用编号；存在有效引用时，只返回这些引用对应的来源。

引用处理优先保障主链路可用性。正常回答完全没有引用标记时，不增加模型或 Embedding 调用，直接把本次实际参考内容作为兜底来源返回。有效与无效编号混合时，只保留有效来源。全部编号无效时，仍返回原回答，但来源列表为空并记录可观测警告。明确拒答始终返回项目固定拒答文案和空来源。

忠实性评估复用现有回答模型，按照可配置比例抽样执行。系统记录回答是忠实、不忠实、跳过评估还是评估失败。首版中，不忠实和评估失败都只用于内部观测，不拦截、不改写回答。公开 API 保持现有顶层结构，仅为来源增加明确的参考编号和内容摘要。

## 用户故事

1. 作为企业员工，我希望回答中的事实带有引用标记，从而知道每条事实由哪段知识库内容支撑。
2. 作为企业员工，我希望引用包含来源文档，从而能够找到权威原文。
3. 作为企业员工，我希望引用包含知识库标识，从而理解来源所属的组织和业务范围。
4. 作为企业员工，我希望引用包含准确的 chunk 标识，从而能够在技术层面追踪证据。
5. 作为企业员工，我希望分页文档的引用包含页码，从而快速定位 PDF 原文。
6. 作为企业员工，我希望引用在存在章节信息时包含章节标题，从而定位非分页文档内容。
7. 作为企业员工，我希望每条来源包含简短摘要，从而在打开完整文档前判断来源是否相关。
8. 作为企业员工，我希望结构化来源包含原始参考编号，从而能与回答中的 `[参考N]` 明确对应。
9. 作为企业员工，我希望同一事实可以标注多个来源，从而看见组合证据。
10. 作为企业员工，我希望重复引用只生成一条来源记录，从而避免来源列表重复和混乱。
11. 作为企业员工，我希望来源按回答中首次出现的顺序排列，从而顺着回答自然核验。
12. 作为企业员工，我希望现有裸格式 `[参考N]` 仍可解析，从而避免旧格式回答突然失去引用能力。
13. 作为企业员工，我希望模型漏标引用时回答仍然可用，从而避免引用问题导致整个问答失败。
14. 作为企业员工，我希望兜底来源只包含实际提供给回答模型的参考内容，从而不会把无关候选误当成证据。
15. 作为企业员工，我希望回答同时包含有效和无效引用时仍保留有效来源，从而避免一个错误编号破坏全部溯源信息。
16. 作为企业员工，我希望全部引用编号无效时系统安全返回空来源，从而不会伪造引用映射。
17. 作为企业员工，我希望知识库拒答不附带来源，从而避免“未找到”与来源列表互相矛盾。
18. 作为企业员工，我希望流程回答列出参考内容中实际可见的全部步骤，从而能够正确执行流程。
19. 作为企业员工，我希望编号规则和条件保持原始顺序，从而不会丢失前后依赖和前置条件。
20. 作为企业员工，我希望模型在存在具体步骤时不要只说“按规定流程操作”，从而得到可执行答案。
21. 作为企业员工，我希望助手只依据参考内容回答，从而不会把通用知识补充成公司制度。
22. 作为企业员工，我希望知识库无法支撑回答时助手明确拒答，从而不会把推测当成公司政策。
23. 作为企业员工，我希望回答正文保留引用标记，从而无需只依赖独立来源列表理解证据关系。
24. 作为 API 调用方，我希望查询响应的顶层结构保持稳定，从而无需进行大范围接口迁移。
25. 作为 API 调用方，我希望 `hit_count` 始终等于最终返回的来源数量，从而保证响应内部一致。
26. 作为 API 调用方，我希望新增来源字段保持向后兼容，从而让旧客户端可以安全忽略。
27. 作为知识库管理员，我希望引用处理只使用已经通过权限过滤的参考内容，从而不会泄露未授权文档。

31. 作为平台运维人员，我希望在评估环境中可以对全部查询执行忠实性评估，从而收集完整数据。
32. 作为平台运维人员，我希望忠实性评估拥有独立超时，从而避免模型服务缓慢时无限拖延查询。
33. 作为平台运维人员，我希望忠实性评估不自动重试，从而避免质量观测放大故障和成本。
34. 作为平台运维人员，我希望评估失败与忠实回答明确区分，从而避免监控数据虚假乐观。
35. 作为平台运维人员，我希望不忠实回答产生警告和指标，从而能够调查回答质量回退。
36. 作为平台运维人员，我希望抽样跳过与评估失败明确区分，从而验证实际抽样率是否符合配置。
37. 作为平台运维人员，我希望记录忠实性评估额外消耗的生成 Token，从而衡量质量监控成本。
38. 作为平台运维人员，我希望观测评估耗时和分数分布，从而基于数据调整抽样和后续策略。
39. 作为安全审查人员，我希望日志不包含完整问题、回答、参考内容、Prompt 和密钥，从而避免监控泄露敏感信息。
40. 作为质量评估人员，我希望忠实性结果只用于内部观测，从而不会让用户误以为模型自评分就是答案正确率。
41. 作为质量评估人员，我希望评估失败时分数为空，从而不会把未成功执行的评估统计为中等分数。
42. 作为维护人员，我希望继续完善现有 V4 而不是复制新的 V5，从而减少完整查询编排的重复维护。
43. 作为维护人员，我希望旧查询管道保留当前 Prompt 行为，从而继续作为回归和降级基线。
44. 作为维护人员，我希望功能完成后 V4 成为默认管道，从而让新部署默认使用完整企业级 RAG 链路。
45. 作为维护人员，我希望复用现有模型、指标和配置基础设施，从而不引入不必要的依赖和客户端。
46. 作为维护人员，我希望引用和评估故障与检索、精排、上下文裁剪及权限逻辑隔离，从而保持现有可靠性保证。
47. 作为开发人员，我希望引用边界条件拥有明确规则，从而避免实现依赖偶然的正则行为。
48. 作为开发人员，我希望来源摘要只展示实际注入 Prompt 的内容，从而不会把被裁剪的文本伪装成模型证据。
49. 作为开发人员，我希望忠实性结果解析严格且确定，从而不会把任意评估模型文本猜测成有效结果。
50. 作为开发人员，我希望本阶段不增加数据库迁移，从而让引用与在线评估独立于会话持久化交付。

## 实施决策

- 本功能在现有 V4 查询管道中完成，不新增 V5 管道。
- 功能完成后 V4 成为默认查询管道；旧版本仍可配置，用于回归和运行时降级。
- V4 使用独立的引用型 System Prompt；旧管道继续使用当前共享 Prompt。
- V4 Prompt 禁止使用通用知识补充公司制度，参考内容不足时必须明确拒答，并禁止推测性表达。
- V4 Prompt 采用标准来源格式 `（来源：[参考N]）`；同一事实的多个来源在一个来源说明中连续列出。
- 回答正文保留引用标记，不增加去除引用后的第二个答案字段。
- Prompt 要求可见的步骤、编号、条件和列表按原顺序完整回答，不能为了简洁用空泛概括替代具体事项。
- 如果参考内容本身被上下文预算截断，回答只能覆盖实际可见内容，并且不能声称不完整流程是完整流程。
- 引用解析支持标准来源格式和现有裸标记 `[参考N]`，允许标记内部存在少量空白，但不支持任意替代语法。
- 引用解析提取全部编号，去除重复编号并保持首次出现顺序。
- 引用语法提取与引用有效性判断是两个职责；只有能够映射本次参考内容的编号才属于有效引用。
- 来源构建继续生成带编号的参考内容，以及本次实际提供给回答模型的完整来源集合。
- 最终来源选择必须在回答生成之后执行。
- 存在一个或多个有效引用时，只返回有效引用对应的来源，并保持首次引用顺序。
- 有效和无效引用混合时忽略无效编号，只返回有效来源。
- 存在引用标记但全部编号无效时，返回原回答和空来源；记录日志与指标，但不向用户抛出错误。
- 正常回答完全没有引用标记时，返回本次全部参考内容作为兜底来源，不增加模型或 Embedding 调用。
- 明确拒答不适用无标注兜底；统一返回项目固定拒答文案、空来源和零命中数量。
- 拒答识别只针对项目明确的拒答语义；正常回答中仅说明某个次要信息未找到时，不能把整个回答转换为拒答。
- 每条来源新增 `reference_index`，用于映射原始参考编号。
- 每条来源新增 `excerpt`，长度最多 200 字符。
- 来源摘要来自实际提供给回答模型的内容，不得展示上下文裁剪已经移除的文本。
- 现有文档、知识库、chunk、页码、章节、排序分和 chunk 序号等元数据继续保留。
- 响应中的 `hit_count` 始终等于最终来源数量。
- 忠实性评估复用现有回答模型和模型凭证。
- 忠实性评估由 `rag_faithfulness_sample_rate` 控制，取值范围为 `0` 到 `1`，默认值为 `0.2`。
- 抽样率为 `0` 时不调用评估模型；为 `1` 时评估所有符合条件的回答。
- 忠实性评估使用独立的 `rag_faithfulness_timeout_seconds` 配置，默认 5 秒。
- 忠实性评估不执行重试。
- 明确拒答不执行忠实性评估。
- 评估器内部状态为忠实、不忠实或评估失败；编排层额外记录抽样跳过状态。
- 有效分数归一化到 `0` 至 `1`；评估失败时分数为空。
- 超时、模型调用失败和输出无法解析均记为评估失败，不能伪装成中等分数的成功结果。
- 首版中，不忠实结果只产生内部警告和指标，不改写或拒绝回答；评估对延迟的最大影响受独立超时限制。
- 公开查询响应不增加忠实性状态或分数字段。
- 本阶段不把在线忠实性评估结果写入数据库。
- 系统记录引用处理结果、有效与无效引用数量、评估状态、分数分布、评估耗时、抽样情况和额外生成 Token。
- 日志可以记录标识、数量、长度、状态、分数、耗时和错误分类，但不能记录完整问题、回答、参考内容、评估 Prompt、密钥或连接信息。
- 权限校验仍然在检索前完成；引用和评估只能消费已授权参考内容，不能扩大搜索范围。
- 现有 HyDE、混合检索、RRF、Reranker 降级、置信度过滤和上下文裁剪行为保持不变。
- 公开查询入口和顶层响应字段保持不变。
- 本功能不需要新增公开端点、第三方依赖、数据库迁移、独立模型客户端或引用修复调用。

## 测试决策

- 测试通过公共接口验证可观察行为，不测试私有方法、内部调用顺序或具体正则实现细节。
- 最高层集成边界是公开 RAG 查询行为，用于验证回答、最终来源、命中数量、拒答语义以及响应不暴露忠实性数据。
- V4 查询服务公共接口是主要编排测试边界，用于验证引用选择和抽样评估与现有检索、精排、过滤、裁剪、生成及拒答行为的组合。
- 引用解析通过其公共提取接口测试，因为它是具有独立业务语义的确定性边界。
- 来源构建和来源选择通过公共接口测试，因为来源溯源是调用方可直接观察的行为，并包含多个必须锁定的边界分支。
- 忠实性评估通过公共评估接口测试。模型属于外部系统边界，可以使用可控测试替身；不为了断言内部调用顺序而 mock 项目内部实现。
- 现有 RAG 查询服务、来源构建、上下文裁剪、Reranker 降级和 Token 指标测试作为服务层测试先例。
- 现有依赖覆盖、权限先于查询以及响应序列化测试作为 API 测试先例。
- 引用解析测试覆盖标准单引用、组合引用、裸标记、重复去重、首次出现顺序、允许空白、无引用以及非引用文本。
- 来源行为测试覆盖精确引用、多引用、有效与无效混合、全部无效、无标注兜底、重复标记、稳定顺序和越界安全。
- 来源元数据测试覆盖参考编号、文档溯源、页码和章节保留、200 字符摘要上限以及摘要仅来自实际模型上下文。
- Prompt 测试覆盖仅根据参考内容回答、标准引用格式、明确拒答、禁止推测和完整有序的流程及列表回答。
- 回归测试验证旧查询管道继续使用原有 Prompt 行为。
- 忠实性评估测试覆盖忠实、不忠实、分数归一化、原因解析、严格格式解析、格式错误、模型异常、超时、不重试和额外 Token 记录。
- 抽样测试覆盖关闭、部分抽样命中、部分抽样跳过和全量评估，并避免依赖不可控的生产随机分支。
- V4 编排测试验证明确拒答返回空来源并跳过评估。
- V4 编排测试验证不忠实和评估失败都不改变最终回答。
- V4 编排测试继续保留无检索结果、裁剪后空上下文、模型空回答、Reranker 降级、置信度过滤和生成失败等现有覆盖。
- 配置测试验证 V4 默认值、默认抽样率、默认超时以及非法配置值校验。
- API 测试验证新增来源字段、稳定顶层结构、命中数量一致性以及不暴露忠实性数据。
- 不增加仅供测试使用的生产绕过逻辑、测试专用功能开关或测试专用服务参数。
- 完成验证包括相关测试、全量测试，以及仓库已配置情况下的 lint 和类型检查。

## 不在范围内

- 回答句子与参考 chunk 之间的逐句 Embedding 匹配。
- 引用缺失或无效时的引用修复、回答重写或额外生成调用。
- 根据不忠实评估结果自动拒绝或替换回答。
- 独立评估模型、评估 API Key、额外模型客户端或模型路由策略。
- 向公开响应暴露忠实性分数或评估状态。
- 在线忠实性结果数据库持久化。
- 会话消息持久化，以及把来源写入助手消息。
- 前端来源卡片、文档预览跳转或兜底来源的视觉展示。
- SSE 流式输出、多轮会话历史、记忆压缩和会话标题。
- 认证、RBAC、租户过滤或知识库权限规则调整。
- 文档解析、分块、索引、Embedding 建库或版本替换调整。
- HyDE、多路问题扩展、向量检索、全文检索、RRF、Reranker、置信度阈值或上下文预算算法调整。
- 新增公开 HTTP 入口或 Controller。
- 新增数据库迁移或第三方依赖。
