# 07 — 记录回答反馈并形成候选闭环

**What to build:** 让用户能够对自己会话中的助手回答提交或覆盖反馈，并让单知识库差评形成可追溯、幂等的评估候选，同时避免多知识库问题被自动错误归属。

**Blocked by:** 03 — 管理标准问题集并标注当前 Chunk

**Status:** resolved

- [x] 新保存的助手消息记录本轮请求的完整知识库范围，历史消息允许范围为空。
- [x] 用户只能反馈自己未删除会话中的助手消息；不存在、他人或非助手消息统一返回 404。
- [x] 反馈值只允许 `1` 或 `-1`，评论可空，客户端不能提交用户身份、问题正文、回答正文或知识库身份。
- [x] 同一用户对同一助手消息只有一条反馈，重复提交在同一事务中覆盖反馈和消息反馈值。
- [x] 原始助手回答和引用继续只保存在消息记录中，反馈和候选不重复保存回答正文。
- [x] 反馈通过同一会话内的创建时间和消息 ID 顺序找到该助手回答之前最近的用户问题。
- [x] 单知识库点踩创建一个 `CANDIDATE`，并通过反馈来源唯一关系防止重复候选。
- [x] 多知识库、未知范围或历史缺失范围的点踩只保存反馈，不自动创建候选。
- [x] 点踩改为点赞时，只归档仍处于 `CANDIDATE` 的关联记录。
- [x] 再次改为点踩时恢复原候选，不插入第二条候选。
- [x] 已进入 `ACTIVE` 或 `NEEDS_REVIEW` 的记录不再随用户反馈变化。
- [x] 日志只记录低基数反馈结果和候选状态变化，不记录问题、回答、评论或敏感标识。
- [x] 测试使用不同用户、会话和知识库范围验证所有权、配对、幂等、候选联动和多知识库边界。
