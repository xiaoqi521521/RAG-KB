# 领域文档

本文说明工程技能在探索和修改代码库前，应如何读取与使用本仓库的领域文档。

## 开始探索前需要读取

- 根目录的 **`CONTEXT.md`**；或者
- 如果根目录存在 **`CONTEXT-MAP.md`**，按照其中的映射读取与当前任务相关的各个 `CONTEXT.md`
- **`docs/adr/`** 中与当前工作区域相关的 ADR
- 多上下文仓库还需要检查各上下文目录下的局部 ADR

如果其中某些文件不存在，直接继续工作，不需要报告缺失，也不要提前建议创建。`/domain-modeling` 技能会在术语或架构决策真正明确时按需创建这些文件。

## 文件结构

单上下文仓库通常采用：

```plain
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

存在根级 `CONTEXT-MAP.md` 时，仓库采用多上下文结构：

```plain
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← 系统级决策
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← 当前上下文的决策
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 使用词汇表中的规范术语

当 Issue 标题、重构建议、假设、测试名称或其他输出涉及领域概念时，必须使用 `CONTEXT.md` 中定义的术语。不要改用词汇表明确要求避免的同义词。

如果需要的概念尚未出现在词汇表中，应先判断是否正在引入项目并不需要的新语言。如果它确实是领域缺口，则记录下来，交由 `/domain-modeling` 处理。

## 明确指出与 ADR 的冲突

如果输出内容与现有 ADR 冲突，必须明确指出，不能静默覆盖原有决策。例如：

> _该方案与 ADR-0007（订单采用事件溯源）冲突，但由于……，值得重新讨论。_
