# 检索层权限过滤设计方案

## 1. 设计目标

本方案在保持现有 route 权限语义的基础上，对齐参考资料，在 `HybridRetriever` 内增加检索层权限过滤。route 层和检索层承担不同职责：route 层保护请求语义，检索层保护实际进入向量、全文和 HyDE 检索的知识库范围。

本方案记录已落地的设计和实现边界。Python 实现已接入 `PermissionService`、`HybridRetriever` 及 v3/v4 HyDE 范围传播；本文件保留方案依据、错误语义和日志约束，作为后续维护基线。

## 2. 已确认边界

### 2.1 route 层

- 请求规范化、去重并保持 `kb_ids` 首次出现顺序。
- 请求的任一知识库无读权限时，整体返回 `403`。
- 权限检查发生在缓存、会话创建、Embedding、检索和模型调用之前。
- 该行为不因检索层支持部分过滤而改变。

### 2.2 检索层

- 权限过滤只增加在 `HybridRetriever`，不建设覆盖所有检索入口的共享权限组件。
- 受保护入口从 `ContextVar` 读取当前用户；上下文不存在时返回 `401`，不能使用默认用户或默认管理员。
- 复用现有 `PermissionService` 作为唯一授权规则来源，不在 `HybridRetriever` 中复制用户、部门、公开知识库和权限等级判断。
- 按单个 `kb_id` 逐库计算有效读权限，不使用跨请求权限缓存。
- 允许部分过滤：只查询有读权限的 `allowed_kb_ids`。
- 过滤后的范围为空时返回 `403`，不执行 Embedding 或任何检索调用。
- 不存在或已删除的知识库在检索过滤中被排除；route 层仍按现有规则对请求中的此类资源返回 `404`。
- 权限数据源不可用时返回 `503`，不能把故障当成无权限过滤。

## 3. 接口与调用链

`HybridRetriever` 保留两层职责：

```plain
HybridRetriever.retrieve(question, requested_kb_ids)
  -> 规范化并去重 requested_kb_ids
  -> 从 ContextVar 读取 CurrentUser
  -> PermissionService 逐库计算 allowed_kb_ids
  -> 记录被过滤范围
  -> allowed_kb_ids 为空时返回 403
  -> 调用内部原始检索

_retrieve(question, allowed_kb_ids)
  -> Embedding
  -> 向量检索
  -> 全文检索
  -> RRF
```

原始检索方法只接收 `allowed_kb_ids`，不读取用户上下文，也不直接查询权限表。它不作为 v2/v3/v4 的业务入口暴露。

`HybridRetrieveResult` 需要携带 `allowed_kb_ids`，供增强检索继续使用：

```plain
HybridRetriever.retrieve
  -> HybridRetrieveResult.hits
  -> HybridRetrieveResult.allowed_kb_ids
  -> EnhancedRetriever 的 HyDE 向量检索
```

v2/v3/v4 使用受保护的混合检索入口。v3/v4 的 HyDE 检索必须复用 `allowed_kb_ids`，不能重新使用原始请求范围。RRF、Reranker、上下文裁剪、引用构建和生成只消费过滤后的命中结果。v1 直接向量管道不新增该 `HybridRetriever` 内部过滤，在线调用继续依赖 route 层权限校验。

## 4. 权限规则

过滤调用现有 `PermissionService`，因此保持以下规则：

- 系统管理员可读取未删除知识库。
- 公开知识库提供读权限，不提供写权限。
- 用户授权和部门授权取 `READ < WRITE < ADMIN` 中最高等级。
- 知识库不存在或已删除时不进入 `allowed_kb_ids`。
- 权限数据源失败时拒绝式返回 `503`。

## 5. 审计日志与指标

参考资料中的过滤审计需要保留用户和被过滤范围信息。根据 ADR-0008，仅检索层权限过滤专用审计日志允许记录：

- `user_id`
- `denied_kb_ids`
- 操作、结果、权限来源
- 请求/允许/拒绝数量
- 耗时和错误类型

这些标识不得扩展到其他权限或认证日志，也不得进入 Prometheus/Grafana 指标标签。日志不记录 JWT、问题、回答、文档正文、文档 ID、对象路径或会话消息。

## 6. 验收标准

- 受保护混合检索能从 `ContextVar` 获取当前用户；缺失时返回 `401`。
- 用户对 `[1, 2]` 仅有 `1` 的读权限时，混合检索只向向量和全文仓储传递 `[1]`。
- 过滤后的 `allowed_kb_ids` 为空时，不发生 Embedding、向量检索、全文检索或模型调用，并返回 `403`。
- 不存在或已删除的知识库不会进入检索范围。
- 权限查询故障返回 `503`，不会降级为无权限或空结果。
- v3/v4 的 HyDE 向量检索与原始混合检索使用相同的 `allowed_kb_ids`。
- 混合检索的原始内部方法不承担权限判断，Repository 只接收已过滤范围。
- route 的多知识库整体拒绝语义保持不变。
- 过滤审计日志包含 `user_id` 和 `denied_kb_ids`，但指标标签不包含这些字段。

## 7. 实现状态

- `PermissionService.filter_readable_kb_ids(...)` 逐库复用现有读权限规则；不存在或已删除的知识库不会进入检索范围。
- `HybridRetriever.retrieve(...)` 从 `ContextVar` 读取用户，去重并过滤范围；`_retrieve(...)` 只接收 `allowed_kb_ids`。
- `app/api/routes/rag.py` 已将同一个 `PermissionService` 注入 v2/v3/v4 混合检索链路；v1 仍保持原有直接向量管道边界。
- 已覆盖部分过滤、空范围短路、`401/403/503`、审计日志和 HyDE 范围传播测试；全量测试结果为 `383 passed, 3 skipped`。
