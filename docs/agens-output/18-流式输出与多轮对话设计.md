# 流式输出与多轮对话设计

本文将 [18-流式输出与多轮对话.md](../references/18-流式输出与多轮对话.md) 的会话和 SSE 方案对齐到当前 FastAPI / LangChain 项目。设计基于现有 V4 查询管道、`kb_chat_session` 和 `kb_chat_message` 模型；不在本阶段实现代码。

## 范围

### In scope

- 新增基于 SSE 的流式 RAG 问答。
- 创建、复用、持久化和读取对话会话及消息。
- 将最近五轮对话历史与本次 RAG 参考内容共同提供给回答模型。
- 流式返回生成状态、回答文本、引用来源和耗时。

### Out of scope

- 基于历史改写当前问题或改变检索 query；检索仍只使用当前 `question`。
- 会话归属校验、租户隔离和跨知识库历史隔离；用户明确将其留待下一阶段。
- 前端界面、WebSocket、断线续传和删除会话接口。
- 替换或重构既有同步 `POST /api/v1/rag/query`。

## 已确认的核心规则

### 会话与历史

- 请求未提供 `session_id` 时创建 UUID 会话；提供时复用该 ID，并更新 `last_active_at`。
- 会话创建时记录本次 `kb_ids`，但它不锁定后续请求的检索范围。每次请求都以当次 `kb_ids` 做权限校验和检索，这与参考实现一致。
- 数据库保存完整对话消息。模型只接收当前问题之前最近五轮、最多十条消息，按时间正序排列；当前 `question` 作为最后一条用户消息单独传入。
- 模型输入顺序为：携带本次 RAG 参考内容的系统消息、对话历史、当前问题。
- 首次成功保存一轮时，以首个问题的前 50 个字符生成会话标题。每个成功轮次保存一条用户消息和一条助手消息，`message_count` 增加 2，并更新 `last_active_at`。
- 仅在完整生成成功后持久化该轮的消息、引用、耗时和生成 token。客户端断开、超时或生成失败时，不写入截断轮次。
- 助手消息的 `sources` 保存本次 `SourceCitation` 列表；`token_count` 保存 provider 返回的生成 token，若不可用则为 `0`。已有 `TokenMetrics` 继续承担全局成本观测。

### 查询与回答

流式链路复用 V4 的检索、Reranker 降级、置信度过滤、上下文裁剪、引用解析和忠实性观测语义，不能复制一套独立的 RAG 管道：

```plain
认证与 kb_ids 权限校验
  -> 创建或复用会话
  -> SSE: status(RETRIEVING, session_id)
  -> V4 检索、精排、过滤、上下文裁剪
  -> 无可用参考内容：SSE token(固定拒答) -> done
  -> SSE: status(GENERATING)
  -> 系统消息(本次参考内容) + 最近五轮历史 + 当前问题
  -> LLM 流式生成，逐片段 SSE token
  -> 聚合完整回答、解析引用、保存本轮消息
  -> SSE: done(sources, latency_ms)
```

无检索结果是正常结束，不发送 `error`，也不进入 `GENERATING`。它发送固定拒答文本的 `token`，再发送 `sources=[]` 且带真实 `latency_ms` 的 `done`。

## HTTP 与 SSE 契约

新增端点，既有同步接口不变：

```plain
GET /api/v1/chat/stream
```

此端点使用 query 参数，命名沿用项目 snake_case：

```plain
question=年假怎么申请
kb_ids=1&kb_ids=2
session_id=<可选 UUID>
```

`GET` 是为了兼容浏览器 `EventSource`；它不改变既有 `POST /api/v1/rag/query` 的 JSON 请求体。

事件顺序和 payload 如下：

| 事件 | 时机 | `data` |
| --- | --- | --- |
| `status` | 开始检索 | JSON：`{"type":"RETRIEVING","message":"正在检索知识库...","session_id":"..."}` |
| `status` | 已获得可用参考内容 | JSON：`{"type":"GENERATING","message":"已找到相关内容，正在生成回答..."}` |
| `token` | 无结果拒答或每个生成文本片段 | 原始文本，不包 JSON |
| `done` | 正常完成 | JSON：`{"sources":[...],"latency_ms":1823}`；`sources` 复用现有 `SourceCitation` 的 snake_case 字段 |
| `error` | 检索、生成或连接超时失败 | JSON：`{"message":"..."}`；仅返回固定用户文案，真实异常写日志 |

若客户端未提供 `session_id`，首个 `status` 必须返回新建的 `session_id`，前端才能在下一次追问复用会话。

流式连接默认超时 60 秒，并通过环境变量配置。超时发送 `error`（`生成超时，请稍后重试`）后关闭连接，且不保存该轮。

## 会话读取接口

本阶段一并提供：

```plain
GET /api/v1/chat/sessions
GET /api/v1/chat/sessions/{session_id}/messages
```

- 会话列表按 `last_active_at` 倒序返回未删除会话。
- 消息列表按 `created_at` 正序返回，供前端还原对话和助手消息的 `sources`。
- 按当前阶段边界，暂不增加会话归属或租户校验；该缺口必须在下一阶段的权限设计中补上。

## 实现边界

- 路由层负责解析 query 参数、预检每个 `kb_id` 的读权限、创建或复用会话，以及返回 `StreamingResponse`。
- 会话读写收敛到独立的 repository / service，不把数据库操作放入 RAG 编排器。
- 流式 RAG 编排在 V4 基础上演进：复用已有检索与引用模块，新增历史加载、`astream` 消费、SSE 编码和成功后的消息持久化。
- 实现前必须按当前安装版本查阅 FastAPI `StreamingResponse` 和 LangChain 聊天模型流式 API 的官方文档，确认取消传播、最终 usage metadata 和异常语义。

## 验收场景

1. 首轮请求依次收到 `RETRIEVING`、`GENERATING`、至少一个 `token`、`done`；首条状态包含可复用的 `session_id`。
2. 使用该 `session_id` 追问时，模型输入含最近五轮历史和本次参考内容，检索仍仅使用当前问题。
3. 第六轮以后，数据库保留全量消息，模型只看到最近十条历史消息且顺序正确。
4. 无命中或无可用上下文时，收到固定拒答 `token` 与空引用 `done`，没有 `GENERATING`。
5. 生成失败或 60 秒超时时，收到固定 `error`，且没有新增用户/助手消息。
6. 成功完成后，保存一对 USER / ASSISTANT 消息；助手消息带来源、耗时和可用的生成 token，列表与消息读取接口能够还原它们。
