# 文档加载四类文件加载过程与逻辑

## 本次说明范围

本文说明当前文档加载层对四类文件的加载过程：

- PDF
- Word（DOC / DOCX）
- TXT
- Markdown（MD / MARKDOWN）

本文只描述 `app/services/document_loader/` 已实现的解析逻辑，不包含上传 API、MinIO 下载、分块、Embedding、向量入库和索引任务状态更新。

## 统一入口

文档加载统一入口是 `DocumentLoaderService.load(file, file_name)`。

整体流程：

```plain
传入文件流和文件名
  -> 根据文件名后缀识别文件类型
  -> 将后缀转为内部大写类型
  -> 找到支持该类型的解析器
  -> 调用 parser.parse(file, file_name, file_type)
  -> 返回 list[Document]
```

文件类型识别规则：

| 文件后缀 | 内部 file_type | 解析器 |
| --- | --- | --- |
| `.pdf` | `PDF` | `PdfParser` |
| `.doc` | `DOC` | `WordParser` |
| `.docx` | `DOCX` | `WordParser` |
| `.txt` | `TXT` | `TxtParser` |
| `.md` | `MD` | `MarkdownParser` |
| `.markdown` | `MARKDOWN` | `MarkdownParser` |

如果文件没有后缀，或后缀没有对应解析器，会抛出 `UnsupportedFileTypeError`。

## 统一输出

四类文件最终都返回：

```plain
list[langchain_core.documents.Document]
```

每个 `Document` 至少包含：

```plain
page_content
metadata.source
metadata.file_type
metadata.page_num
```

可选字段：

```plain
metadata.section_title
```

metadata 由 `build_metadata()` 统一构造，目的是避免不同解析器生成不一致的字段。

## PDF 加载过程

PDF 使用 `PdfParser`，底层复用 `MinerULoaderClient` 调用 MinerU 官方 LangChain SDK 的 `MinerULoader`。

支持前置条件：

- `MINERU_ENABLED=true`
- `MINERU_MODE=sdk`
- `MINERU_API_TYPE=precision` 或 `flash`
- 使用 `precision` 时必须配置 `MINERU_API_KEY`

加载流程：

```plain
收到 PDF 文件流
  -> 检查 MinerU 是否启用
  -> 检查集成模式是否为 sdk
  -> 根据 MINERU_API_TYPE 转换 SDK mode
  -> 将文件流写入带 .pdf 后缀的临时文件
  -> 创建 MinerULoader
  -> 调用 loader.load()
  -> 删除临时文件
  -> 将 MinerU SDK 返回的 Document 列表转换为项目标准 Document
```

PDF 调用 MinerULoader 的关键参数：

```plain
source      = 临时 PDF 文件路径
mode        = precision 或 flash
token       = MINERU_API_KEY，未配置时为 None
language    = ch
timeout     = MINERU_TIMEOUT_SECONDS
split_pages = True
```

`split_pages=True` 表示 PDF 按页拆分。MinerU SDK 返回的每个 `Document` 通常对应 PDF 的一页。

PDF 转换逻辑：

- 读取 SDK 返回的 `Document.page_content`。
- 空内容会被跳过。
- 优先从 SDK metadata 的 `page` 字段读取页码。
- 如果没有 `page`，使用当前列表序号作为 `page_num`。
- 优先读取 SDK metadata 的 `section_title`。
- 如果没有 `section_title`，从 Markdown 标题行中尝试提取。
- MinerU 返回内容按 Markdown 处理，再复用 `MarkdownParser._strip_markdown()` 清理基础 Markdown 标记。

PDF 输出特点：

```plain
一个 PDF 通常返回多个 Document
每个 Document 对应一页或一个 SDK 拆分结果
page_num 尽量保留真实页码
page_content 为清理后的可检索正文
```

异常边界：

- MinerU 未启用：抛出 `ExternalParserError`
- mode 不支持：抛出 `ExternalParserError`
- precision 模式缺少 API Key：抛出 `ExternalParserError`
- SDK 调用失败：抛出 `ExternalParserError`
- SDK 返回没有有效正文：抛出 `EmptyDocumentError`

## Word 加载过程

Word 文件使用 `WordParser`，支持 `.doc` 和 `.docx`，底层复用 `MinerULoaderClient` 调用 MinerU。

加载流程与 PDF 基本一致：

```plain
收到 DOC / DOCX 文件流
  -> 检查 MinerU 配置
  -> 将文件流写入带原始后缀的临时文件
  -> 创建 MinerULoader
  -> 调用 loader.load()
  -> 删除临时文件
  -> 转换为项目标准 Document
```

Word 调用 MinerULoader 的关键参数：

```plain
source      = 临时 Word 文件路径
mode        = precision 或 flash
token       = MINERU_API_KEY，未配置时为 None
language    = ch
timeout     = MINERU_TIMEOUT_SECONDS
split_pages = False
```

Word 与 PDF 的关键差异是：

```plain
PDF:  split_pages=True
Word: split_pages=False
```

当前实现中，Word 不按页强制拆分，先由 MinerU SDK 以 `split_pages=False` 返回 Markdown 内容，再按参考项目的标题阈值规则切分为逻辑章节。这样做是因为 Word 文件通常没有稳定的真实页码语义，强行分页容易影响后续引用的一致性。

Word 转换逻辑：

- 读取 SDK 返回的 `Document.page_content`。
- 空内容跳过。
- 使用 Markdown 标题切分逻辑处理 Word 内容。
- 遇到新的一级/二级标题时，当前累计章节超过 200 字才收束为一个 `Document`。
- 当前累计章节不足 200 字时，不单独生成 `Document`，继续累积到后续章节。
- 短章节合并到后续章节时，`section_title` 使用最后遇到的标题。
- 使用列表序号作为逻辑 `page_num`。
- 使用 Markdown 清理逻辑得到最终 `page_content`。

Word 输出特点：

```plain
一个 Word 文件可能返回多个 Document
page_num 使用逻辑章节序号，从 1 开始
section_title 来自当前逻辑章节最后遇到的标题
```

异常边界与 PDF 一致。

## TXT 加载过程

TXT 使用项目内轻量解析器 `TxtParser`，不走 MinerU。

不走 MinerU 的原因：

- TXT 已经是纯文本，不需要 OCR 或版面分析。
- 使用 MinerU 会增加外部依赖、网络耗时和失败面。
- 当前需求只需要编码处理、换行归一化和基础有效性检查。

加载流程：

```plain
收到 TXT 文件流
  -> 读取原始 bytes
  -> 尝试 UTF-8 解码
  -> 如果替换字符比例过高，尝试 GBK 解码
  -> 去除 UTF-8 BOM
  -> 将 CRLF / CR 换行统一为 LF
  -> 去掉首尾空白
  -> 检查是否为空
  -> 检查控制字符比例
  -> 返回单个 Document
```

编码判断逻辑：

- 首先用 UTF-8 解码，错误字符用替换字符表示。
- 如果替换字符 `\ufffd` 占比不超过 2%，认为 UTF-8 可接受。
- 如果替换字符占比超过 2%，再尝试 GBK。

文本有效性检查：

- 清理后为空：抛出 `EmptyDocumentError`。
- 控制字符比例超过 5%：抛出 `DocumentParseError`。
- 换行和制表符属于正常文本控制字符，不计入异常比例。

TXT 输出特点：

```plain
一个 TXT 文件返回 1 个 Document
page_num 固定为 1
page_content 为归一化后的全文
```

metadata 示例：

```plain
source    = 原始文件名
file_type = TXT
page_num  = 1
```

## Markdown 加载过程

Markdown 使用项目内轻量解析器 `MarkdownParser`，支持 `.md` 和 `.markdown`。

不使用通用 loader 的原因：

- 项目需要自定义 `file_type`、`page_num`、`section_title` 等 metadata。
- 使用通用 loader 后仍然要再包一层 metadata 适配。
- 当前 Markdown 需求集中在标题切分和基础标记清理，自定义实现更直接。

加载流程：

```plain
收到 Markdown 文件流
  -> 按 UTF-8 解码
  -> 将 CRLF 换行统一为 LF
  -> 按标题和 100 字阈值切分逻辑章节
  -> 对每个章节清理 Markdown 标记
  -> 跳过空章节
  -> 为每个章节生成一个 Document
```

标题切分逻辑：

- 支持一级标题 `#` 和二级标题 `##` 作为章节边界。
- 当前正则也能识别三级标题，但三级标题不会作为切分边界。
- 代码块中的 `#` 不会被当作标题。
- 遇到新章节标题时，只有当前累计章节超过 100 字，才收束上一个章节。
- 当前累计章节不足 100 字时，不单独生成 `Document`，继续累积到后续章节。
- 短章节合并到后续章节时，`section_title` 使用最后遇到的一级/二级标题。
- 如果全文没有标题但存在正文，则整篇作为一个逻辑章节。

代码块处理逻辑：

```plain
遇到 ``` 开头的行
  -> 切换 in_code_block 状态
  -> 代码块内容保留在当前章节
  -> 代码块内部不参与标题判断
```

Markdown 清理逻辑：

- 代码块替换为 `[代码块]`。
- 行内代码去掉反引号，保留可见文本。
- 图片替换为 `[图片]`。
- 链接保留可见文字。
- 去掉标题标记。
- 去掉基础加粗、斜体标记。
- 去掉无序列表和有序列表前缀。
- 将连续三行以上空行压缩为两行。

Markdown 输出特点：

```plain
一个 Markdown 文件可能返回多个 Document
每个 Document 对应一个满足最小长度阈值的逻辑章节
page_num 使用章节序号，从 1 开始
section_title 来自当前逻辑章节最后遇到的标题
```

异常边界：

- 所有章节清理后都为空：抛出 `EmptyDocumentError`。

## 四类文件的差异总结

| 类型 | 解析器 | 是否依赖 MinerU | 返回粒度 | page_num 来源 |
| --- | --- | --- | --- | --- |
| PDF | `PdfParser` | 是 | 通常一页一个 Document | SDK metadata `page`，缺失时用序号 |
| Word | `WordParser` | 是 | 一个逻辑章节一个 Document | 章节序号 |
| TXT | `TxtParser` | 否 | 单个 Document | 固定为 1 |
| Markdown | `MarkdownParser` | 否 | 一个逻辑章节一个 Document | 章节序号 |

## 当前设计边界

- 文档加载层只负责把文件流变成 `list[Document]`。
- 文档加载层不做分块，分块由后续 chunking 层负责。
- 文档加载层不写数据库，不访问 MinIO，不调用 Embedding。
- 复杂文档不做低质量本地兜底；MinerU 不可用时直接失败，避免用户误以为复杂文档已经高质量解析。
- `page_count` 不放入单个 `Document.metadata`，因为 `list[Document]` 已经表达了解析出的文本单元集合。
