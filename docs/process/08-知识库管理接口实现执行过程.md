## 3.2 实际代码执行流程

### 实际总体执行链路

本次实现与 Plan 1.2、Spec 2.4 的主链路保持一致，最终落地为：

```plain
用户请求进入 FastAPI
  -> get_current_user() 注入当前用户
  -> PermissionService 校验读/写权限
  -> KnowledgeBaseService 编排业务动作
  -> Repository / MinioStorageService / IndexService 执行底层能力
  -> 返回 ApiResponse 或 StreamingResponse
```

上传文档主链路：

```plain
POST /api/v1/kb/{kb_id}/documents
  -> PermissionService.require_write(kb_id, user)
  -> KnowledgeBaseService.upload_document(kb_id, file, user)
  -> 校验文件名、类型、大小
  -> MinioStorageService.upload(...)
  -> DocumentRepository.create(...)
  -> IndexService.submit_index_task(doc_id)
  -> 返回 202 + DocumentUploadResponse(status=PENDING)
```

状态查询主链路：

```plain
GET /api/v1/kb/{kb_id}/documents/{doc_id}/status
  -> PermissionService.require_read(kb_id, user)
  -> KnowledgeBaseService.get_index_status(kb_id, doc_id)
  -> DocumentRepository.get(doc_id)
  -> 校验 doc.kb_id == kb_id
  -> IndexTaskRepository.get_latest_by_doc_id(doc_id)
  -> 返回 IndexStatusResponse
```

文档列表主链路：

```plain
GET /api/v1/kb/{kb_id}/documents
  -> PermissionService.require_read(kb_id, user)
  -> KnowledgeBaseService.list_documents(kb_id)
  -> DocumentRepository.list_by_kb(kb_id)
  -> 路由层将 KbDocument 转换为 DocumentItem
  -> 返回 ApiResponse[list[DocumentItem]]
```

下载主链路：

```plain
GET /api/v1/kb/{kb_id}/documents/{doc_id}/download
  -> PermissionService.require_read(kb_id, user)
  -> KnowledgeBaseService.download_document(kb_id, doc_id)
  -> MinioStorageService.download(document.minio_path)
  -> StreamingResponse(BytesIO(content))
  -> 设置 Content-Disposition
```

删除主链路：

```plain
DELETE /api/v1/kb/{kb_id}/documents/{doc_id}
  -> PermissionService.require_write(kb_id, user)
  -> KnowledgeBaseService.delete_document(kb_id, doc_id)
  -> DocumentRepository.mark_deleted(doc_id)
  -> ChunkRepository.delete_by_doc_id(doc_id)
  -> MinioStorageService.delete(document.minio_path)
  -> 返回 ApiResponse[None]
```

重建索引主链路：

```plain
POST /api/v1/kb/{kb_id}/documents/{doc_id}/reindex
  -> PermissionService.require_write(kb_id, user)
  -> KnowledgeBaseService.reindex_document(kb_id, doc_id)
  -> DONE 文档保持发布状态；非 DONE 文档 reset_for_reindex(doc_id)
  -> IndexService.reindex_document(doc_id)
  -> 返回 202 + ApiResponse[str]
```

### 完整落地流程

#### 1. 路由层入口

`app/api/routes/knowledge_bases.py` 使用 `APIRouter` 定义所有知识库管理接口。路由层只做 HTTP 入参接收、依赖注入、权限入口调用和响应组装，不直接操作数据库或 MinIO。

实际依赖装配：

```plain
get_current_user()
  -> 来自 app/api/dependencies.py

get_permission_service(session)
  -> KnowledgeBaseRepository
  -> KbPermissionRepository
  -> PermissionService

get_knowledge_base_service(session, settings)
  -> DocumentRepository / IndexTaskRepository / ChunkRepository
  -> MinioStorageService
  -> DocumentLoaderService / ChunkService / EmbeddingService
  -> IndexService
  -> KnowledgeBaseService
```

与 Spec 对齐说明：

- 当前 Spec 已改为复用 `app/api/dependencies.py` 和 `app/core/context.py`，不再建议新增 `app/services/user_context.py`。
- `CurrentUser` 只保留 `user_id`、`department_id`、`role` 三个字段，贴近参考文献中的用户上下文粒度。

#### 2. 权限校验

所有文档相关接口在进入业务服务前先执行权限校验：

```plain
上传 / 删除 / 重建索引 -> require_write(...)
状态查询 / 文档列表 / 下载 -> require_read(...)
```

权限来源：

```plain
管理员角色
公开知识库
用户显式授权
部门显式授权
```

读权限规则：

```plain
ADMIN -> 放行
公开知识库 -> 放行
用户或部门存在任意权限 -> 放行
否则 -> 403
```

写权限规则：

```plain
ADMIN -> 放行
用户或部门权限为 WRITE / ADMIN -> 放行
公开知识库不自动获得写权限
否则 -> 403
```

#### 3. 上传与索引提交

上传文档由 `KnowledgeBaseService.upload_document(...)` 编排：

```plain
校验 file.filename
  -> 根据扩展名识别 file_type
  -> 校验文件大小
  -> 上传 MinIO
  -> 创建 kb_document
  -> 调用 IndexService.submit_index_task(doc_id)
```

失败补偿：

```plain
MinIO 上传成功
  -> 文档记录创建或索引任务提交失败
  -> 如果文档已创建，则 mark_failed(doc_id, error_msg)
  -> 删除刚上传的 MinIO 对象
  -> 继续向上抛出原异常
```

这个补偿逻辑是本次实现相对 Spec 的强化点，避免出现“文件已上传、文档记录存在，但没有索引任务”的悬挂状态。

#### 4. MinIO 存储服务

`MinioStorageService` 使用当前项目已经初始化的同步版 MinIO SDK 客户端。由于 FastAPI 路由和 service 是 async，所有 SDK 访问都通过 `asyncio.to_thread(...)` 包装。

实际行为：

```plain
upload(...)
  -> await file.read()
  -> object_key = kb/{kb_id}/{short_uuid}-{file_name}
  -> asyncio.to_thread(_upload)
  -> _upload 内部 ensure bucket + put_object

download(...)
  -> asyncio.to_thread(_download)
  -> get_object
  -> read bytes
  -> close + release_conn

delete(...)
  -> asyncio.to_thread(_delete)
  -> remove_object
  -> 删除失败只记录 warning，不阻断主流程
```

#### 5. 状态查询、删除、重建

状态查询读取两个数据源：

```plain
kb_document
kb_index_task 最新任务
```

返回字段：

```plain
doc_id
file_name
status
error_msg
chunk_count
token_count
indexed_at
retry_count
```

删除文档使用混合策略：

```plain
文档记录 -> 软删除
chunk 向量数据 -> 硬删除
MinIO 原始文件 -> 删除对象
```

重建索引不直接处理 chunk 版本切换，而是：

```plain
reset_for_reindex(doc_id)
  -> document.status = PENDING
  -> document.error_msg = None
  -> IndexService.reindex_document(doc_id)
```

真正的新旧版本策略仍由上一阶段 `IndexService` 执行，避免两个服务重复处理索引细节。

首次上传文档触发的是 `INDEX` 任务，索引完成后沿用文档初始版本 `1`；只有手动重建索引触发 `REINDEX` 任务时，才由 `IndexService` 将版本递增到下一版。

## 3.3 核心代码片段及深度讲解

### 1. 路由层依赖装配

```python
def get_knowledge_base_service(
    session: AsyncSession = Depends(get_db),
    settings: Settings = Depends(get_settings),
) -> KnowledgeBaseService:
    document_repository = DocumentRepository(session)
    task_repository = IndexTaskRepository(session)
    chunk_repository = ChunkRepository(session)
    storage_service = MinioStorageService(client=get_minio(), bucket=settings.minio_bucket)
    loader_service = DocumentLoaderService(
        [
            TxtParser(),
            MarkdownParser(),
            PdfParser(settings=settings),
            WordParser(settings=settings),
        ]
    )
    index_service = IndexService(
        document_repository=document_repository,
        task_repository=task_repository,
        chunk_repository=chunk_repository,
        storage_service=storage_service,
        loader_service=loader_service,
        chunk_service=ChunkService(),
        embedding_service=EmbeddingService(get_embeddings(), get_redis()),
    )
    return KnowledgeBaseService(
        knowledge_base_repository=KnowledgeBaseRepository(session),
        permission_repository=KbPermissionRepository(session),
        document_repository=document_repository,
        task_repository=task_repository,
        chunk_repository=chunk_repository,
        storage_service=storage_service,
        index_service=index_service,
        max_upload_file_size_mb=settings.max_upload_file_size_mb,
    )
```

讲解：

- 路由层通过 FastAPI `Depends(...)` 组合本阶段需要的服务。
- `DocumentRepository`、`IndexTaskRepository`、`ChunkRepository` 同时传给 `KnowledgeBaseService` 和 `IndexService`，保证上传创建文档后能直接提交现有索引管道。
- `IndexService` 仍是索引链路唯一编排者，`KnowledgeBaseService` 不重复实现解析、分块、Embedding 或版本清理逻辑。
- 这里没有使用 `BackgroundTasks`，因为 `IndexService.submit_index_task(...)` 内部已经负责后台投递。
- 请求级 `IndexService` 在启动后台任务前会提交当前事务；后台任务通过 `background_index_service_factory` 创建独立 `AsyncSessionLocal()` 和独立仓储，避免复用请求级 session。

### 2. 上传接口

```python
@router.post("/{kb_id}/documents", status_code=status.HTTP_202_ACCEPTED)
async def upload_document(
    kb_id: int,
    file: UploadFile = File(...),
    user: CurrentUser = Depends(get_current_user),
    permission_service: PermissionService = Depends(get_permission_service),
    kb_service: KnowledgeBaseService = Depends(get_knowledge_base_service),
) -> ApiResponse[DocumentUploadResponse]:
    await permission_service.require_write(kb_id, user)
    document = await kb_service.upload_document(kb_id, file, user)
    return ApiResponse.ok(DocumentUploadResponse.submitted(document.id, document.file_name))
```

讲解：

- 文件上传使用 FastAPI 推荐的 `UploadFile = File(...)`。
- 入口先调用 `require_write(...)`，确保无写权限用户不会进入上传、写库或索引提交流程。
- 接口返回 `202 Accepted`，表达“文档已接收，索引后台执行中”。
- 返回体只包含 `doc_id`、`file_name`、`PENDING` 和提示信息，前端后续通过状态接口轮询。

### 3. 上传编排与失败补偿

```python
async def upload_document(self, kb_id: int, file: UploadFile, user: CurrentUser) -> KbDocument:
    file_name = file.filename
    if not file_name:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="文件名不能为空")

    file_type = self._detect_file_type(file_name)
    file_size = self._get_file_size(file)
    if file_size > self.max_upload_file_size_bytes:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="文件大小超过限制")

    minio_path = await self.storage_service.upload(kb_id, file)
    document: KbDocument | None = None
    try:
        document = await self.document_repository.create(
            kb_id=kb_id,
            file_name=file_name,
            file_type=file_type,
            file_size=file_size,
            minio_path=minio_path,
            uploaded_by=user.user_id,
        )
        await self.index_service.submit_index_task(document.id)
        return document
    except Exception as exc:
        if document is not None:
            await self.document_repository.mark_failed(document.id, str(exc))
        await self.storage_service.delete(minio_path)
        raise
```

讲解：

- 主流程顺序与参考文献一致：先存 MinIO，再创建文档记录，再提交索引任务。
- 文件类型只允许 `.pdf`、`.docx`、`.md`、`.txt`，避免不支持格式进入解析链路。
- 如果 MinIO 上传成功，但数据库写入或索引任务提交失败，会尝试删除刚上传的对象。
- 如果文档记录已经创建，则把文档标记为 `FAILED`，避免出现用户能看到 `PENDING` 但永远没有索引任务推进的状态。

### 4. 权限读写分离

```python
async def require_read(self, kb_id: int, user: CurrentUser) -> None:
    knowledge_base = await self.knowledge_base_repository.get(kb_id)
    if knowledge_base is None or knowledge_base.is_deleted:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="知识库不存在")

    if user.is_admin or knowledge_base.is_public:
        return

    permission = await self.get_highest_permission(kb_id, user)
    if permission is None:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="无权访问该知识库")


async def require_write(self, kb_id: int, user: CurrentUser) -> None:
    knowledge_base = await self.knowledge_base_repository.get(kb_id)
    if knowledge_base is None or knowledge_base.is_deleted:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="知识库不存在")

    if user.is_admin:
        return

    permission = await self.get_highest_permission(kb_id, user)
    if permission not in {KbPermissionLevel.WRITE.value, KbPermissionLevel.ADMIN.value}:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="无文档管理权限")
```

讲解：

- 读权限允许公开知识库通过。
- 写权限不因为知识库公开而放行，必须是管理员或显式 `WRITE / ADMIN`。
- 读写权限分离后，上传、删除、重建这类修改动作可以统一使用 `require_write(...)`，状态、列表、下载使用 `require_read(...)`。

### 5. MinIO 同步 SDK 的 async 包装

```python
async def upload(self, kb_id: int, file: UploadFile) -> str:
    file_name = file.filename or "uploaded-file"
    content = await file.read()
    object_key = f"kb/{kb_id}/{uuid4().hex[:8]}-{file_name}"
    content_type = file.content_type or "application/octet-stream"

    def _upload() -> None:
        self._ensure_bucket_exists()
        self.client.put_object(
            bucket_name=self.bucket,
            object_name=object_key,
            data=BytesIO(content),
            length=len(content),
            content_type=content_type,
        )

    await asyncio.to_thread(_upload)
    logger.info("[MinIO] 上传成功：path=%s", object_key)
    return object_key
```

讲解：

- FastAPI 的 `UploadFile` 读取使用 `await file.read()`。
- MinIO Python SDK 是同步客户端，真正的 `put_object(...)` 被放入 `asyncio.to_thread(...)`，避免阻塞事件循环。
- object key 使用 `kb/{kb_id}/{short_uuid}-{file_name}`，与参考文献中按知识库隔离原文件路径的设计一致。
- 上传前会懒检查 bucket 是否存在，不存在则创建。

### 6. 下载接口使用 StreamingResponse

```python
@router.get("/{kb_id}/documents/{doc_id}/download")
async def download_document(
    kb_id: int,
    doc_id: int,
    user: CurrentUser = Depends(get_current_user),
    permission_service: PermissionService = Depends(get_permission_service),
    kb_service: KnowledgeBaseService = Depends(get_knowledge_base_service),
) -> StreamingResponse:
    await permission_service.require_read(kb_id, user)
    file_name, content = await kb_service.download_document(kb_id, doc_id)
    encoded_name = quote(file_name)
    return StreamingResponse(
        BytesIO(content),
        media_type="application/octet-stream",
        headers={"Content-Disposition": f"attachment; filename*=UTF-8''{encoded_name}"},
    )
```

讲解：

- 下载也先走 `require_read(...)`，保证无读权限用户拿不到原始文件。
- service 返回 `file_name + bytes`，路由层负责 HTTP 响应形态。
- `Content-Disposition` 使用 `filename*=UTF-8''...`，对中文文件名更友好。
- 当前实现把 MinIO 内容读为 bytes 再通过 `BytesIO` 返回，适合本阶段；超大文件后续可升级为真正流式转发。

### 7. 状态查询聚合文档与最新任务

```python
async def get_index_status(self, kb_id: int, doc_id: int) -> IndexStatusResponse:
    document = await self._get_document_in_kb(kb_id, doc_id)
    latest_task = await self.task_repository.get_latest_by_doc_id(doc_id)
    return IndexStatusResponse(
        doc_id=document.id,
        file_name=document.file_name,
        status=document.status,
        error_msg=document.error_msg,
        chunk_count=document.chunk_count,
        token_count=document.token_count,
        indexed_at=document.indexed_at,
        retry_count=latest_task.retry_count if latest_task is not None else 0,
    )
```

讲解：

- 文档状态来自 `kb_document.status`。
- 重试次数来自最新 `kb_index_task.retry_count`。
- `_get_document_in_kb(...)` 会校验 `doc_id` 是否属于当前 `kb_id`，避免用户拿一个合法 `doc_id` 越权查询其他知识库文档。

### 8. 文档删除与重建

```python
async def delete_document(self, kb_id: int, doc_id: int) -> None:
    document = await self._get_document_in_kb(kb_id, doc_id)
    await self.document_repository.mark_deleted(doc_id)
    await self.chunk_repository.delete_by_doc_id(doc_id)
    await self.storage_service.delete(document.minio_path)


async def reindex_document(self, kb_id: int, doc_id: int) -> int:
    document = await self._get_document_in_kb(kb_id, doc_id)
    if document.status != DocumentStatus.DONE.value:
        await self.document_repository.reset_for_reindex(doc_id)
    return await self.index_service.reindex_document(doc_id)
```

讲解：

- 删除文档采用参考文献的混合策略：文档记录软删除、向量 chunk 硬删除、MinIO 对象删除。
- MinIO 删除失败在 `MinioStorageService.delete(...)` 内部只记录 warning，不阻断主流程。
- 重建索引对已发布文档只提交 `IndexService.reindex_document(...)`，不重置主文档状态；未发布文档才调用 `reset_for_reindex(...)` 清理旧错误状态。

## 3.7 重建索引后台会话修订

联调 `POST /api/v1/kb/{kb_id}/documents/{doc_id}/reindex` 时，接口本身返回 `202 Accepted`，但控制台出现后台任务异常：

```plain
Task exception was never retrieved
sqlalchemy.exc.InvalidRequestError: This session is in 'prepared' state; no further SQL can be emitted within this transaction.
```

根因：

- 重建索引接口使用请求级 `AsyncSession` 创建 `IndexTask` 后，`IndexService._launch_task(...)` 立即把同一个 `IndexService` 实例投递到后台。
- 该实例内部持有的仓储仍绑定请求级 `AsyncSession`。
- 请求收尾提交事务时，后台任务同时继续使用同一个 session 查询/更新任务状态，触发 SQLAlchemy 事务状态冲突。

修订后的边界：

```plain
请求级 KnowledgeBaseService.reindex_document(...)
  -> DONE 文档保持发布状态；非 DONE 文档 reset_for_reindex(doc_id)
  -> IndexService.reindex_document(doc_id)
       -> 创建 IndexTask(PENDING)
       -> 提交当前请求事务
       -> asyncio.create_task(_run_launched_task(...))
  -> 后台任务通过 background_index_service_factory 创建独立 AsyncSessionLocal()
  -> 独立 IndexService.run_task(task_id, doc_id)
```

本次同步调整：

- `app/services/indexing.py`：新增 `background_service_factory` 和 `commit_before_launch`，后台任务执行时不再复用请求级服务实例。
- `app/api/routes/knowledge_bases.py`：新增 `_build_index_service(...)` 和 `background_index_service_factory()`，为后台索引任务创建独立数据库会话并在任务结束后提交/回滚。
- `tests/services/test_indexing.py`：新增回归测试，覆盖“启动前提交当前事务”和“后台任务使用独立服务工厂”两个边界。

补充状态可见性要求：后台任务进入执行态后，会立即提交 `task(RUNNING)`；首次索引或未发布文档重建还会提交 `document(PROCESSING)`。已发布文档 REINDEX 不修改主文档状态，避免在线查询被 `DONE` 过滤挡住。

## 3.8 首次索引版本修订

后续联调发现，首次上传文档后 `kb_document.version` 会从初始值 `1` 变为 `2`。该问题不属于知识库接口层直接写错版本，而是接口层提交首次索引任务后，索引管道统一按 `document.version + 1` 生成本次 chunk 版本，导致首次 `INDEX` 和重建 `REINDEX` 没有区分。

修订后的接口链路语义：

```plain

  -> IndexService.submit_index_task(...) 创建 INDEX 任务

重建索引
  -> DONE 文档保持发布状态，非 DONE 文档 reset_for_reindex(...)
  -> IndexService.reindex_document(...) 创建 REINDEX 任务
  -> REINDEX 完成后 document.version 递增为 2、3、...
```

本次同步调整：

- `tests/services/test_indexing.py`：首次索引断言 `document.version == 1`、`chunk.doc_version == 1`。
- `tests/services/test_indexing.py`：新增重建索引回归测试，断言 `REINDEX` 后版本递增。
- `docs/specs/09.5-索引管道建立spec.md`：同步索引管道版本策略。

## 3.9 执行态状态可见性修订

上传文件后，在文档加载阶段直接查询数据库发现 `kb_document.status` 和 `kb_index_task.status` 仍然是 `PENDING`。根因是：

- `submit_index_task(...)` 只负责创建 `task(PENDING)` 并投递后台任务。
- 后台 `run_task(...)` 开始时确实会写入 `task(RUNNING)`、`document(PROCESSING)`。
- 但 Repository 只 `flush()`，后台独立 session 原先直到整个索引任务完成后才 `commit()`。
- 因此加载、分块、Embedding 等长耗时阶段，其他数据库连接仍只能看到已提交的 `PENDING`。

修订后的执行链路：

```plain
上传接口
  -> 创建 document(PENDING)
  -> 创建 task(PENDING)
  -> 提交当前请求事务
  -> 投递后台任务

后台任务启动
  -> task(RUNNING)
  -> document(PROCESSING)
  -> 立即提交后台会话
  -> 下载 MinIO 原文
  -> 文档加载 / 分块 / Embedding / chunk 入库
  -> document(DONE) / task(DONE)
```

本次同步调整：

- `app/services/indexing.py`：新增 `commit_after_status_change` 钩子。
- `app/api/routes/knowledge_bases.py`：后台索引服务传入 `background_session.commit`，让执行态状态立即对外可见。
- `tests/services/test_indexing.py`：新增回归测试，断言执行态提交发生在 MinIO 下载前。
