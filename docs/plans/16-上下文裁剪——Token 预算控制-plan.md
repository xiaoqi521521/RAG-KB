# 16-上下文裁剪——Token 预算控制 Plan

理解信心已达到 95%：本阶段直接承接第 15 章 Reranker 精排结果，参考资料已经明确目标是把进入模型的参考上下文控制在固定 Token 预算内，同时保留高相关内容并记录成本指标。

本文基于 [16-上下文裁剪——Token 预算控制.md](../references/16-上下文裁剪——Token%20预算控制.md)、[三阶段生成.md](../prompt/三阶段生成.md) 的 Plan 阶段规则，以及前序混合检索、查询改写和 Reranker 精排计划，梳理 LangChain / FastAPI 版本中的上下文裁剪与 Token 预算控制计划。

## 1.1 任务背景

混合检索、查询改写和 Reranker 精排会提高候选 chunk 的相关性，但最终候选仍可能超出模型上下文预算，导致请求成本升高、响应变慢，甚至让模型在过长上下文中忽略关键证据。企业知识库问答需要在有限预算内优先保留最能支撑答案的内容，并让每次查询的上下文消耗可记录、可监控。

本阶段目标是在生成回答前增加上下文裁剪能力：按已排序候选的相关性顺序选择内容，控制进入 Prompt 的参考内容规模，并在预算不足时有明确边界。该能力不改变检索、精排和权限判断，只负责把已经允许访问、已经排序的候选压缩成可控上下文。

## 1.2 业务流程

### 1.2.1 总体执行链路

上下文裁剪查询流程：

1. 用户发起知识库问答请求，系统完成认证、知识库权限校验、查询改写、混合检索和 Reranker 精排。
2. 系统取得已按相关性排序的候选 chunk，候选必须已经过权限硬过滤并保留来源元数据。
3. 系统读取本次查询可用于参考内容的 Token 预算，作为进入生成模型前的上限。
4. 系统按候选排序从高到低选择 chunk，优先保留最相关内容，直到预算即将耗尽。
5. 如果第一个高相关 chunk 本身超过预算，系统保留可用部分，避免有候选却完全没有上下文。
6. 如果后续 chunk 放不进剩余预算，系统停止继续追加，避免低优先级内容挤占成本。
7. 系统记录候选数量、选中数量、上下文 Token 消耗和预算使用情况。
8. 系统把裁剪后的上下文交给引用组装和回答生成；如果没有可用上下文，则进入固定拒答。

### 1.2.2 关键实现

上下文裁剪只处理已经排序好的候选列表，不重新计算相关性，也不改变候选的权限范围。排序来源可以是 Reranker 精排结果，也可以是 Reranker 降级后的 RRF 融合结果；裁剪阶段只信任前序排序并按顺序取用。

预算控制需要区分“参考内容预算”和“整次模型请求预算”。本阶段重点控制参考内容部分，避免候选 chunk 无限制拼接；系统提示词、用户问题、对话历史和回答预留空间属于整体 Prompt 预算的一部分，后续技术方案中应统一配置，但 Plan 阶段不展开具体算法。

当候选内容超过预算时，系统应优先保证高相关内容进入上下文。对普通超预算 chunk，后续内容直接舍弃；对第一个 chunk 就超预算的场景，可以截取其前段可用内容，保证回答生成至少有一段证据。截取后仍必须保留原始来源信息，让后续引用能够追溯到文档、知识库、页码、章节或 chunk。

裁剪结果需要和引用顺序保持一致。最终进入上下文的内容顺序就是后续引用来源的展示基础，不能出现回答参考序号与 sources 顺序不一致的情况。

Token 消耗记录是本阶段的重要业务结果。系统需要记录每次查询实际进入上下文的 Token 数、候选到选中数量变化和预算使用比例，便于后续成本控制、监控看板和评估分析。记录过程不能输出完整文档正文、访问密钥或敏感业务内容。

无候选、候选全被裁剪为空、或预算配置不可用时，系统不得让模型凭通用知识补全公司制度。它应沿用知识库问答的拒答原则，明确说明未找到可支撑回答的相关内容。

## 1.3 业务边界

### In Scope

- 在现有知识库问答链路中加入生成前上下文裁剪，不新增前端页面和公开查询路径。
- 裁剪输入来自 Reranker 精排结果，或 Reranker 降级后的 RRF 排序结果。
- 按固定参考内容预算限制进入模型的 chunk 总量，避免无限拼接候选内容。
- 按候选相关性顺序优先保留高质量内容，预算耗尽后停止追加。
- 支持首个 chunk 超预算时保留可用部分，避免有高相关候选却无上下文。
- 保留裁剪后 chunk 的文档、知识库、页码、章节和 chunk 来源信息。
- 记录上下文 Token 消耗、候选数量、选中数量、预算上限和预算使用情况。
- 无可用上下文时保持固定拒答，不允许模型脱离知识库自由回答。
- 为后续 Spec 和实现预留测试重点：预算裁剪、首个 chunk 超预算、引用元数据不丢失、空上下文拒答和 Token 统计。

### Out of Scope

- 不重新实现向量检索、全文检索、RRF 融合、查询改写或 Reranker 精排。
- 不改变权限校验位置，不把权限控制交给 Prompt、模型或前端。
- 不实现完整引用溯源和防幻觉二次校验；这些属于后续引用溯源与防幻觉阶段。
- 不实现 SSE 流式输出、多轮对话记忆压缩或会话历史长期管理。
- 不新增用户可见的预算配置界面、成本报表页面或管理员看板。
- 不把 Token 预算控制作为答案质量置信度判断；它只控制上下文规模。
- 不引入新的长期存储结构，除非后续 Spec 证明现有日志或监控能力无法承载指标。
- 不为了节省 Token 删除引用所需的关键来源元数据。

## 1.4 方案取舍

### 推荐方案：排序后贪心裁剪，预算内优先保留高相关 chunk

推荐把上下文裁剪放在 Reranker 精排之后、引用组装和回答生成之前。系统按前序排序从高到低选择 chunk，在预算内尽可能多保留高相关内容；若首个 chunk 超出预算，则保留可用部分并保留来源元数据。

选择该方案的原因是业务语义清晰：检索和精排负责“哪些内容更相关”，裁剪负责“哪些内容能放进预算”。它不扩大权限范围、不改变召回结果，只控制进入模型的参考内容规模，便于测试、监控和后续成本优化。

### 备选方案一：直接把 Reranker Top N 全部放入上下文

这种方案实现最简单，但无法控制 Token 成本，也可能在文档 chunk 偏长时超出预算。它还会增加模型忽略关键证据的风险，不适合作为企业知识库的稳定策略。

### 备选方案二：按每个 chunk 固定截断后全部保留

这种方案可以让更多候选进入上下文，但会破坏原始片段完整性，容易让引用内容缺少上下文前后关系。它也可能让低相关 chunk 占用预算，不如按相关性顺序优先保留更稳妥。

### 备选方案三：让生成模型自行忽略不重要内容

这种方案把预算控制和证据选择交给模型隐式处理，成本不可控，也难以测试。项目要求核心业务逻辑保持在服务层显式编排，因此不推荐。

本 Plan 推荐采用“排序后贪心裁剪，预算内优先保留高相关 chunk”。
