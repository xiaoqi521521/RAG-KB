# 15-Reranker 精排——召回后的精准排序与降级 Plan

本文基于 [15-Reranker 精排——召回后的精准排序与降级.md](../references/15-Reranker%20精排——召回后的精准排序与降级.md)、[三阶段生成.md](../prompt/三阶段生成.md) 的 Plan 阶段规则，以及当前已形成的混合检索与查询改写计划，梳理 LangChain / FastAPI 版本中的 Reranker 精排升级计划。

本阶段目标是在“查询改写 + 混合检索 + RRF 融合”之后加入精排能力，让进入回答上下文的 chunk 更贴近用户问题。精排是召回后的质量增强层，不替代权限过滤、不替代 RRF 融合，也不能因为外部精排服务超时而导致整条问答链路不可用。

## 1.1 任务背景

混合检索和查询改写会提升召回覆盖面，但它们会一次性带回较多候选内容，其中可能包含语义相近但不真正回答问题的 chunk。企业知识库问答需要把有限的上下文窗口留给最相关、最可引用、最能支撑答案的内容，因此需要在召回后加入 Reranker 精排。

Reranker 的价值是把“用户问题”和“候选段落”成对比较，给出更细粒度的相关性排序。它通常比向量相似度和全文排名更准，但调用成本和延迟更高，所以只能用于少量候选，并且必须具备超时降级能力。

本阶段要解决的核心问题：

- 提升最终进入回答上下文的 chunk 相关性，减少弱相关内容干扰生成。
- 在精排失败、超时、限流或返回异常时，回退到 RRF 融合排序结果。
- 在精排后过滤低置信度结果，避免明显不相关 chunk 进入模型。
- 保持引用来源可追溯，精排只改变排序和分数，不丢失文档、页码、章节和 chunk 信息。
- 保持权限隔离仍由检索层硬过滤完成，精排不能扩大用户可访问范围。
- 记录精排耗时、候选数量、返回数量、降级状态和成本指标，便于后续监控与评估。

## 1.2 业务流程

### 1.2.1 总体执行链路

Reranker 精排查询流程：

1. 用户发起知识库问答请求，系统完成问题校验和知识库读权限校验。
2. 系统按已规划的查询改写和混合检索流程召回候选 chunk，并完成 RRF 融合排序。
3. 系统从融合结果中截取少量候选，送入精排模型进行相关性重排。
4. 精排成功时，系统按精排分数重新排序，并只保留最相关的候选。
5. 精排失败或超时时，系统记录降级原因，并直接沿用 RRF 融合排序结果。
6. 系统对排序后的候选做低置信度过滤，过滤掉明显不相关内容。
7. 系统把过滤后的候选交给上下文裁剪和引用组装流程，最终基于知识库内容生成回答。
8. 如果没有任何有效候选，系统返回固定拒答，不调用模型自由发挥。

### 1.2.2 完整业务流程

#### 查询入口保持稳定

本阶段不新增前端页面，也不新增公开问答入口。调用方仍通过现有知识库问答入口提交问题和知识库范围。Reranker 是服务端内部查询链路的一环，对调用方表现为回答质量和引用排序提升，而不是新的用户操作。

入口层仍然先完成：

- 问题不能为空。
- 知识库范围不能为空且格式合法。
- 用户必须具备目标知识库读权限。
- 权限失败时直接终止请求，不进入查询改写、混合检索、精排或生成。

这个顺序不能调整。精排只能处理已经过权限硬过滤的候选 chunk，不能参与权限判断，也不能接触用户无权访问的内容。

#### 候选来源

精排的输入来自前序查询链路，而不是直接面向全量文档检索。候选应已经满足以下条件：

- 来自用户有读权限的知识库。
- 来自当前可用文档版本。
- 来自已完成索引且未删除的文档。
- 已经过向量检索、全文检索和 RRF 融合排序。
- 可能包含原始问题、HyDE 文本或多路扩展问题带来的召回结果。

精排不负责扩大召回范围。它只在前序候选集合内重新判断“哪几条更适合进入上下文”。

#### 精排执行

精排阶段会把用户原始问题与每个候选 chunk 的正文进行成对比较。模型返回的相关性分数用于重新排序候选，分数越高越优先进入后续上下文。

精排执行应遵循以下业务原则：

- 候选数量必须受控，只处理 RRF 融合后的少量高排位结果。
- 原始问题始终作为精排问题，不使用 HyDE 假设性回答替代用户问题。
- 精排只使用 chunk 内容和必要元数据，不把无关业务数据发送给外部服务。
- 精排结果必须能映射回原始 chunk，不能丢失引用来源。
- 精排分数只表达当前问题和候选段落的相关性，不代表文档质量或权限级别。

#### 超时与失败降级

Reranker 是外部模型能力，存在网络抖动、限流、返回异常和响应过慢的风险。它不能成为问答主链路的单点阻塞。

推荐降级顺序：

1. 精排成功时，使用精排排序和精排分数。
2. 精排超时、失败、返回空结果或结果无法映射时，回退到 RRF 融合排序。
3. 回退后仍按候选数量上限截取结果，避免把过多 chunk 交给后续上下文。
4. 降级状态进入日志和监控，用户响应不暴露内部异常细节。

降级后的回答仍然来自真实知识库候选，只是排序精度从精排回到 RRF。系统不能因为精排失败直接报错，也不能跳过检索后让模型自由回答。

#### 低置信度过滤

精排后需要过滤掉相关性过低的候选。低分 chunk 往往会污染上下文，让模型误以为问题有答案，进而增加幻觉风险。

过滤规则应满足：

- 低于置信度阈值的 chunk 不进入后续上下文。
- 如果过滤后仍有有效候选，保留这些候选继续生成。
- 如果所有候选都低于阈值，可以保留最高分候选进入后续防幻觉链路，也可以直接进入拒答；具体策略在后续技术方案中明确。
- 无论采用哪种策略，最终回答必须基于真实候选内容，不能用精排分数本身生成答案。

本阶段建议把“低置信度过滤”和“无结果拒答”作为两个相邻但不同的业务判断：过滤负责减少噪声，拒答负责在知识库无法支撑回答时给出明确反馈。

#### 上下文与引用衔接

精排后的候选继续进入后续上下文裁剪、引用组装和回答生成流程。这个阶段必须保留来源信息：

- 文档标识。
- 文档名称。
- 知识库标识。
- chunk 标识。
- 页码或章节标题。
- 相关片段摘要。
- 当前用于排序的相关性分数。

引用顺序应与最终进入上下文的候选顺序一致，避免答案中的“参考 1、参考 2”和响应 sources 顺序不一致。

#### 无结果与拒答

如果 RRF 融合后没有候选，系统直接拒答，不进入精排。  
如果精排和过滤后没有可用候选，系统也应拒答或进入后续防幻觉拒答判断，不调用模型凭通用知识补全公司制度。

固定拒答语义保持与前序查询管道一致：明确说明知识库未找到相关内容，并建议用户调整提问或联系相关部门。拒答响应不应包含伪造引用。

#### 日志与可观测性

本阶段需要记录精排相关的关键指标：

- 精排是否启用。
- 输入候选数量。
- 精排返回数量。
- 最终保留数量。
- 精排耗时。
- 是否发生降级。
- 降级原因分类。
- 低置信度过滤数量。
- 精排模型调用成本或 token 使用量。

日志不能输出访问密钥、完整 Prompt、大段 chunk 内容或敏感文档正文。可记录问题长度、候选数量、分数范围、耗时和状态。

### 1.2.3 关键分支与边界条件

#### 分支一：混合检索召回宽泛但精排收敛

用户问题较具体时，混合检索可能召回同一主题下的多个相关制度片段。精排应把真正回答问题的 chunk 排到前面，让后续上下文优先包含直接证据。

#### 分支二：精确关键词命中但语义不贴题

全文检索可能因为关键词相同召回弱相关段落。精排应结合用户问题整体意图重新判断，降低只包含关键词但不能回答问题的 chunk 排名。

#### 分支三：多路改写召回结果互相竞争

原始问题、HyDE 和多路扩展可能召回不同方向的候选。RRF 负责融合多路排名，精排负责在融合后的候选中再次按原始问题意图筛选。

#### 分支四：精排服务超时

精排服务超过允许等待时间时，系统记录降级状态，并使用 RRF 排序结果继续生成。用户不应感知为查询失败。

#### 分支五：精排返回异常

如果精排返回空结果、数量异常、分数缺失或无法映射原候选，系统视为精排失败，回退到 RRF 结果。

#### 分支六：候选数量不足

如果前序候选数量已经少于或等于最终需要数量，可以跳过精排或仍执行精排；后续技术方案需明确取舍。无论是否跳过，都必须保持输出排序、引用和日志语义一致。

#### 分支七：低置信度候选

如果精排后候选分数整体偏低，系统应减少或拒绝使用这些候选，避免模型基于弱相关内容强行回答。

#### 分支八：权限和来源保持

精排不能新增候选，也不能改变候选的知识库归属、文档归属和来源元数据。任何用户无权访问的 chunk 都不能因为精排或降级进入候选集合。

## 1.3 业务边界

### In Scope

本阶段必须覆盖的业务范围：

- 在现有知识库问答链路中加入召回后精排，不新增前端页面和公开查询路径。
- 精排输入来自 RRF 融合后的候选结果，不直接访问全量文档。
- 精排使用用户原始问题判断候选相关性，不使用 HyDE 假设内容替代用户问题。
- 精排成功时按相关性分数重排候选，并控制最终保留数量。
- 精排失败、超时、限流、空返回或结果不可用时，回退到 RRF 融合排序。
- 精排后执行低置信度过滤，减少弱相关 chunk 对生成的干扰。
- 保留 chunk 的文档、知识库、页码、章节和摘要等引用元数据。
- 无候选或有效候选不足时保持固定拒答，不允许模型脱离知识库补全答案。
- 记录精排耗时、候选数量、返回数量、降级状态、过滤数量和成本指标。
- 增加后续测试覆盖精排成功排序、超时降级、异常降级、低置信度过滤、引用不丢失和权限不绕过。

### Out of Scope

本阶段不实现或不展开：

- 不新增公开 HTTP 接口、前端交互或用户可见的精排开关。
- 不重新实现向量检索、全文检索、RRF 融合或查询改写。
- 不改变权限校验位置，不把权限控制交给 Prompt、模型或前端。
- 不实现精确 Token 预算裁剪；该能力属于后续上下文裁剪阶段。
- 不实现完整引用溯源、防幻觉二次校验和事实性评估；这些属于后续章节。
- 不实现 SSE 流式输出、多轮对话记忆或会话标题生成。
- 不把精排分数解释为最终答案置信度，也不把它作为唯一拒答依据。
- 不新增文档解析、分块、Embedding 入库或索引重建流程。
- 不引入独立搜索引擎或新的长期存储结构。

## 1.4 方案取舍

### 推荐方案：RRF 后精排，失败回退到 RRF

推荐把 Reranker 放在 RRF 融合之后、上下文裁剪之前。前序检索负责尽量召回，RRF 负责多路融合，Reranker 负责在少量候选中精细排序，后续上下文裁剪和引用组装继续消费统一候选列表。

优点：

- 最贴合参考资料中“召回后少量候选精排”的定位。
- 与第 13 章和第 14 章自然衔接，避免重复设计召回逻辑。
- 降级路径清晰：精排不可用时直接使用 RRF 排序。
- 精排只影响排序和候选数量，不影响权限、来源和拒答底线。

代价：

- 每次查询可能增加外部模型调用，需要控制候选数量和超时时间。
- 精排分数和 RRF 分数语义不同，后续响应和日志需要明确区分。

### 备选方案一：向量和全文召回后分别精排再融合

这种方案可以更早过滤每路召回结果，但会让多路排序逻辑复杂化，也会增加模型调用次数。它不利于控制成本和延迟，不推荐作为第一版。

### 备选方案二：不接入精排，只增加 RRF 候选数量

这种方案实现最轻，但无法解决“召回多但排序不够准”的核心问题。增加候选数量还会挤占上下文窗口，可能降低回答质量。

### 备选方案三：把精排交给生成 Prompt 判断

让生成模型自己从多个 chunk 中判断相关性，看似减少一个外部能力，但会把排序、证据选择和回答生成混在一起，难以测试和降级，也不符合服务层显式编排要求。因此不推荐。

本 Plan 推荐采用“RRF 后精排，失败回退到 RRF”。

## 1.5 与当前链路的衔接计划

后续技术方案可围绕以下交付物拆分，但本 Plan 不固定具体实现细节：

- 精排能力封装：负责调用外部精排模型、处理返回结果、映射原候选和记录耗时。
- 降级策略：负责在超时、异常、空结果和映射失败时回退到 RRF 排序。
- 置信度过滤：负责按相关性阈值过滤弱相关 chunk，并明确全低分时的处理策略。
- 查询链路接入：负责把精排放在混合检索之后、上下文裁剪之前。
- 成本与监控：负责记录精排请求数量、耗时、降级次数、过滤数量和模型成本。
- 测试用例：覆盖精排排序、候选数量控制、超时降级、异常降级、低分过滤、引用元数据保留和权限边界。

建议后续技术方案重点明确：

- 精排输入候选数量和最终保留数量。
- 精排超时时间和降级结果的排序规则。
- 精排分数、RRF 分数和响应 sources 中分数的语义。
- 低置信度阈值的默认策略，以及全低分时是保留最高分进入后续防幻觉，还是直接拒答。
- 精排调用失败时的日志字段和监控指标。
- 精排模型不可用时对用户响应、引用和耗时字段的影响。

## 1.6 验收方向

本 Plan 不直接修改代码，但后续技术方案和实现应能验证以下行为：

- 有读权限用户发起查询时，系统在 RRF 融合后执行精排。
- 任一知识库无读权限时，请求在检索前失败，不触发精排。
- 精排输入只包含用户已授权知识库中的候选 chunk。
- 精排成功时，最终候选按精排相关性重新排序。
- 精排只改变排序和分数，不丢失文档、知识库、页码、章节和 chunk 来源信息。
- 精排超时时，系统回退到 RRF 排序结果继续生成。
- 精排返回空结果或无法映射候选时，系统回退到 RRF 排序结果继续生成。
- 低于置信度阈值的候选不会进入后续上下文，除非后续技术方案明确保留最高分候选用于防幻觉判断。
- 无有效候选时，系统返回固定拒答，不调用模型自由发挥。
- 正常响应中的引用顺序与进入上下文的候选顺序一致。
- 日志能区分精排成功、精排降级、低置信度过滤和无候选拒答。
- 精排耗时、候选数量、返回数量、最终保留数量和降级原因可被监控或统计。
- 文档文件名符合 Plan 阶段要求，使用 `-plan.md` 后缀。

## 1.7 下一步文档建议

完成本 Plan 后，下一份技术方案应重点回答：

- 精排能力在当前服务层中的输入输出结构。
- 外部精排模型的调用格式、超时、错误分类和返回解析规则。
- 候选数量控制如何与混合检索、查询改写和上下文裁剪衔接。
- 低置信度过滤是否独立封装，以及全低分时的最终业务策略。
- 精排分数是否写入响应 sources，以及如何避免用户误解为答案置信度。
- 降级日志、成本指标和评估指标如何命名与记录。
- 需要新增哪些测试，尤其是权限不绕过、精排超时、异常降级、引用不丢失和拒答边界。
