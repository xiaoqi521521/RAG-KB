# 14-查询改写——HyDE 与多路扩展 Plan

本文基于 [14-查询改写——HyDE 与多路扩展.md](/D:/Code/python/Practical_Project/rag-kb/docs/references/14-查询改写——HyDE%20与多路扩展.md)、[三阶段生成.md](/D:/Code/python/Practical_Project/rag-kb/docs/prompt/三阶段生成.md) 的 Plan 阶段规则，以及当前已形成的基础查询与混合检索计划，梳理 LangChain / FastAPI 版本中的查询改写升级计划。

本阶段目标是在“向量检索 + 全文检索 + RRF 融合”的基础上，加入 HyDE 假设性回答和多路查询扩展，让用户的口语化提问、缩写提问、换词提问更容易召回企业知识库中的真实内容。查询改写只增强召回入口，不改变权限隔离、引用来源、拒答策略和最终回答必须基于知识库上下文的底线。

## 1.1 任务背景

基础 RAG 查询管道已经解决了“用户提问后能按权限检索知识库并生成回答”的主链路，混合检索进一步补齐了向量检索和全文检索各自的短板。但在企业知识库场景中，用户真实提问经常和文档表达不一致：

- 用户说“怎么请假”，文档写“假期申请流程”。
- 用户说“新人第一天要干嘛”，文档写“入职第一天领取工牌、电脑并完成环境配置”。
- 用户说“代码提交规范”，文档可能分散写成“提交信息格式”“分支管理策略”“合并请求要求”。

如果只拿原始问题直接检索，即使已经有向量和全文两路召回，也可能因为表达太短、语义过口语化、关键词不完整而漏掉相关 chunk。参考文献第 14 章给出的增强方向是两类查询改写：

- HyDE：先让模型生成一段“假设知识库里可能存在的回答”，再用这段更接近文档正文表达的文本参与向量检索。
- 多路查询扩展：把原始问题改写成多个不同角度但意图一致的问题，分别检索后合并排序。

本阶段要解决的核心问题：

- 提升口语化、模糊化、缩写化问题的召回率。
- 在不扩大用户权限范围的前提下，让改写后的查询也只能检索已授权知识库。
- 改写失败、模型超时或缓存不可用时，查询链路必须回退到原始问题检索。
- 控制额外模型调用带来的延迟和 Token 成本，避免查询改写成为主链路稳定性瓶颈。
- 为后续 Reranker 精排提供更丰富的候选，但不提前实现精排逻辑。

当前项目中可复用的基础包括：

- 基础查询服务：已经负责拒答、上下文组装、引用返回和模型生成。
- 混合检索服务：已经负责向量召回、全文召回和 RRF 融合。
- Embedding 服务：已经封装缓存、批处理、维度校验和 provider 重试。
- Redis：已经用于加速类缓存，可承接 HyDE 与多路扩展结果缓存。
- 配置对象：已经集中管理 RAG TopK、RRF 参数、查询管道版本和上下文预算。
- 权限服务：已经在检索前完成知识库读权限硬校验。

因此，本阶段不重新设计完整查询管道，而是在检索入口前增加“改写候选生成”，再把原始问题、HyDE 文本和扩展问题作为多路召回输入交给现有混合检索能力处理。

## 1.2 业务流程

### 1.2.1 总体执行链路

查询改写增强流程：

1. 用户发起知识库问答请求，请求仍包含原始问题和目标知识库范围。
2. 系统先完成输入校验和知识库读权限校验，未授权请求在改写和检索前终止。
3. 系统对原始问题做基础标准化，保留它作为必选检索输入。
4. 在配置允许时，系统生成 HyDE 假设性回答，并把它作为语义检索增强输入。
5. 在配置允许时，系统生成多个多路扩展问题，并把它们作为额外检索输入。
6. 系统分别对原始问题、HyDE 文本和扩展问题执行混合检索，所有检索仍受同一知识库权限范围限制。
7. 系统把多路召回结果按 RRF 融合、去重和排序，得到统一候选列表。
8. 后续回答生成、引用组装、无结果拒答和耗时统计继续沿用现有查询链路。

### 1.2.2 完整业务流程

#### 查询入口保持稳定

本阶段不新增面向前端或调用方的新问答入口。用户仍通过现有 RAG 查询入口提交问题和知识库范围。查询改写是服务端内部召回增强能力，调用方不需要知道每个候选 chunk 是由原始问题、HyDE 文本还是扩展问题召回。

入口层仍然负责：

- 校验问题不能为空。
- 校验知识库范围不能为空且格式合法。
- 对每个知识库执行读权限校验。
- 权限失败时直接拒绝请求，不进入查询改写、向量化、全文检索或聊天模型生成。

这个顺序不能调整。查询改写会调用模型生成新文本，如果在权限校验前执行，既浪费成本，也会让无权限请求触发不必要的外部服务调用。

#### 原始问题保留

原始问题必须始终参与检索。HyDE 和多路扩展只能增强召回，不能替代用户原始表达。这样可以避免模型改写偏离意图后污染检索结果，也能保证查询改写失败时主链路仍可运行。

系统应记录原始问题与改写候选的关系，但不把完整改写文本默认暴露给前端。必要的可观测信息进入日志和评估数据，例如是否启用 HyDE、扩展问题数量、改写耗时、缓存命中情况和最终候选数量。

#### HyDE 生成

HyDE 的业务含义是：系统先根据用户问题生成一段简短的“假设性答案”，这段答案不作为最终回答展示给用户，只用于检索。它的价值在于把短问题转换成更像企业文档正文的表达，从而提升向量检索命中率。

示例流程：用户问“新员工第一天要干嘛”时，系统先生成一段类似“新员工入职第一天通常需要完成报到、领取工牌和电脑、配置办公账号、阅读入职指引并参加部门介绍”的假设性回答，再用这段文本参与向量检索，从而更容易召回“入职第一天流程”相关 chunk。

HyDE 只影响检索候选，不直接作为答案来源。最终回答仍必须基于实际召回 chunk。若知识库没有相关内容，即使 HyDE 文本看起来像答案，也不能把它返回给用户。

HyDE 生成应有以下业务边界：

- 输出应短而聚焦，避免生成很长内容消耗过多 Token。
- 输出必须保留原始问题意图，不补充无关主题。
- 相同问题和相同策略下可短期缓存，降低重复调用成本。
- 生成失败、超时、空结果或输出明显不可用时，回退到仅使用原始问题检索。

#### 多路查询扩展

多路查询扩展的业务含义是：系统把一个问题改写成几个不同角度但意图一致的问题，让检索同时覆盖同义词、正式文档表述、口语表达和相关子维度。

示例流程：用户问“代码提交规范”时，系统可以扩展出“提交信息格式有什么要求”“分支管理和合并请求需要遵守哪些规则”“研发代码提交前需要完成哪些检查”等不同角度的问题，再把多路检索结果统一融合排序。

多路扩展应有以下业务边界：

- 扩展问题数量默认控制在较小范围，避免召回成本线性膨胀。
- 扩展问题必须去重，不能和原始问题完全相同。
- 扩展问题不得扩大用户意图，例如把“年假申请”扩成“全部人事制度”。
- 解析失败、输出为空或质量异常时，系统回退到原始问题检索。

#### 多路检索与融合

查询改写后，系统会形成多种检索输入：

- 原始问题。
- HyDE 假设性回答。
- 多路扩展问题。

每一路输入都需要在同一授权知识库范围内检索。权限过滤必须仍然发生在检索执行层，不能因为改写文本来自模型就放松知识库过滤。

融合逻辑应沿用混合检索阶段的 RRF 思路：每一路检索结果都按排名参与融合，同一个 chunk 被多路召回时只保留一条，分数累加后排序提升。这样可以让“多个改写都命中同一 chunk”的结果自然排到更前面。

融合后传给回答生成的仍是统一候选列表。生成层只关心最终排序、chunk 内容和引用元数据，不需要知道具体召回通道。

#### 缓存与成本控制

查询改写会增加聊天模型调用，因此必须把成本控制放进业务流程：

- HyDE 和扩展问题可以按问题文本、策略版本和模型配置生成缓存 key。
- 缓存只作为加速层，读写失败不能影响主查询。
- 缓存过期时间应短于长期业务文档周期，避免策略调整后长期复用旧改写。
- 日志需要记录缓存命中、模型调用次数和改写耗时，便于后续 Token 成本统计。

本阶段只规划查询改写结果缓存，不规划完整查询结果缓存。完整查询结果缓存会涉及权限、文档版本、引用变化和会话上下文，后续应单独设计。

#### 降级与失败处理

查询改写的失败不应导致整次问答失败。推荐降级顺序：

1. HyDE 失败时，去掉 HyDE 输入，继续使用原始问题和可用的扩展问题。
2. 多路扩展失败时，去掉扩展问题，继续使用原始问题和可用的 HyDE 输入。
3. 两种改写都失败时，完全回退到第 13 章混合检索链路。
4. 原始问题检索所需的向量化或数据库检索失败时，仍按现有查询错误语义返回服务不可用或检索失败。

也就是说，查询改写是可降级增强层；基础检索和权限过滤仍是主链路。不能因为 HyDE 失败而跳过检索，也不能因为扩展问题失败而直接拒答。

#### 无结果与拒答

如果所有可用检索输入融合后仍没有候选 chunk，服务继续返回固定拒答，不调用聊天模型自由发挥。HyDE 文本和扩展问题不属于可信知识库上下文，不能作为兜底答案。

如果有候选 chunk，但内容不足以回答问题，生成 Prompt 仍要求模型说明“未找到相关内容”，不能用 HyDE 假设文本补全公司制度。

#### 日志与可观测性

本阶段需要比混合检索多记录查询改写相关指标：

- 是否启用 HyDE。
- HyDE 是否命中缓存。
- HyDE 生成耗时和是否降级。
- 是否启用多路扩展。
- 扩展问题数量。
- 扩展生成耗时和是否降级。
- 原始问题、HyDE、扩展问题各自召回数量。
- 融合前候选数量、融合后候选数量和最终进入上下文数量。

日志不能输出完整 Prompt、访问密钥、大段 chunk 内容或未经脱敏的敏感文档内容。改写文本是否进入日志应谨慎，默认只记录长度、数量和状态。

### 1.2.3 关键分支与边界条件

#### 分支一：口语化问题由 HyDE 补强

用户问题很短或偏口语化时，HyDE 生成更接近文档正文的假设性回答。系统用它参与向量检索，召回“正式文档表述”相关 chunk。最终答案仍从真实 chunk 生成。

#### 分支二：精确主题由多路扩展补强

用户问题只有一个主题词时，多路扩展可以补出流程、要求、限制、操作入口等不同角度，提升全文和向量两路召回机会。多个扩展问题命中同一 chunk 时，该 chunk 在融合排序中提升。

#### 分支三：改写结果偏离意图

如果模型生成的改写明显偏离原始问题，可能召回无关内容。系统应通过短输出、保留原始问题、限制扩展数量、后续 Reranker 和生成侧防幻觉规则降低风险。本阶段不引入复杂语义审核模型，只在流程上保证原始问题不会被替换。

#### 分支四：改写服务超时或失败

HyDE 或多路扩展调用外部模型超时、限流或返回空内容时，系统记录降级原因，继续使用已有检索输入。查询改写失败不是用户可见错误。

#### 分支五：缓存不可用

Redis 读取或写入失败时，系统只记录日志并继续调用模型或继续主流程。缓存不能成为查询链路的强依赖。

#### 分支六：权限与版本过滤

所有由改写文本触发的检索仍必须使用用户已授权知识库范围，并只召回当前版本、已完成索引且未删除文档的 chunk。任何扩展问题都不能突破权限硬过滤。

#### 分支七：无有效候选

如果原始问题、HyDE 和扩展问题都没有召回候选，服务直接拒答并返回空引用。此时不调用聊天模型，也不返回 HyDE 假设性回答。

## 1.3 业务边界

### In Scope

本阶段必须覆盖的业务范围：

- 在现有 RAG 查询链路中加入查询改写增强，不新增前端页面和外部 HTTP 路径。
- 保留原始问题作为必选检索输入，避免改写偏离后覆盖用户真实意图。
- 支持 HyDE 假设性回答，用于增强向量召回，但不作为最终答案或可信引用。
- 支持多路查询扩展，用于从不同表达角度召回候选。
- 改写后的所有检索仍复用知识库读权限、当前版本、已完成索引和未删除过滤。
- 多路召回结果通过 RRF 融合去重，最终输出统一候选列表。
- 查询改写失败、超时、空结果或缓存不可用时，回退到原始问题混合检索。
- 为 HyDE 和多路扩展规划短期缓存，降低重复问题的模型调用成本。
- 记录改写耗时、缓存命中、降级状态、各路召回数量和最终候选数量。
- 增加测试覆盖改写降级、缓存失效、原始问题保留、多路去重、权限不被绕过和无结果拒答。
- 同步更新后续 Spec / Process 文档，记录最终策略开关、配置参数、日志字段和验证结果。

### Out of Scope

本阶段不实现或不展开：

- 不新增公开查询接口、前端交互或用户可见的“改写问题列表”展示。
- 不把 HyDE 假设性回答作为最终答案、引用来源或防幻觉兜底材料。
- 不实现 Reranker 精排、Reranker 超时和 RRF 降级；这些属于第 15 章。
- 不实现精确 Token 预算裁剪；这些属于第 16 章。
- 不实现完整引用溯源、防幻觉二次校验和事实性评估；这些属于第 17 章。
- 不实现 SSE 流式输出、多轮对话记忆或会话标题生成；这些属于第 18 章。
- 不新增数据库表，不改离线索引、文档解析、分块、Embedding 入库或文档重建流程。
- 不引入新的检索引擎、复杂中文分词插件或独立工作流引擎。
- 不做完整查询结果缓存，也不把权限控制交给 Prompt、前端或模型改写规则。

## 1.4 方案取舍

### 推荐方案：查询改写作为混合检索前的增强层

推荐把查询改写放在混合检索之前：先生成原始问题、HyDE 文本和扩展问题，再分别执行混合检索，最后统一 RRF 融合。查询服务仍只接收最终候选，生成和引用链路保持稳定。

优点：

- 最贴合参考文献第 14 章的目标，能同时提升语义召回和关键词召回。
- 与第 13 章混合检索衔接自然，后续第 15 章 Reranker 可以直接消费更多候选。
- 原始问题始终保留，降级路径清晰。
- 改写逻辑集中在检索增强层，生成层不会被 HyDE 假设文本污染。

代价：

- 每次查询可能增加一次或多次模型调用，必须控制超时、缓存和扩展数量。
- 检索次数会随改写候选增加，需要记录耗时并避免 TopK 过大。

### 备选方案一：只实现 HyDE，不实现多路扩展

这种方案实现较轻，适合快速提升口语化问题的语义召回。但它对精确关键词、制度条款、英文缩写、多角度主题覆盖帮助有限，也没有完整承接参考文献中的多路查询价值。

### 备选方案二：只实现多路扩展，不实现 HyDE

这种方案对关键词变体和问题改写有帮助，成本也更容易估算。但面对“用户问题很短、文档表达很完整”的场景，多路问题仍可能不如 HyDE 假设性回答贴近正文语义。

### 备选方案三：在生成阶段使用改写文本

把 HyDE 文本或扩展问题一起放进回答 Prompt，看似可以给模型更多线索，但会把模型生成的假设内容混入可信上下文，增加幻觉风险。该方案不符合企业知识库“回答必须基于检索上下文”的要求，因此不推荐。

本 Plan 推荐采用“查询改写作为混合检索前的增强层”，并要求所有改写能力都具备失败降级和成本记录。

## 1.5 与当前代码的衔接计划

后续 Spec 可围绕以下交付物拆分，但本 Plan 不固定具体实现细节：

- 查询改写服务：负责 HyDE 生成、多路扩展、输出清洗、去重、短期缓存和降级。
- 增强检索服务：负责把原始问题、HyDE 文本和扩展问题送入现有混合检索，并统一融合排序。
- 配置项：负责控制是否启用 HyDE、是否启用多路扩展、扩展数量、改写超时、缓存过期时间和最大改写文本长度。
- 缓存集成：负责存取 HyDE 与多路扩展结果，缓存失败不影响主链路。
- 查询服务接入：负责选择查询管道版本，并保持 API 响应字段和拒答行为稳定。
- 测试用例：覆盖正常增强、单项改写失败、全部改写失败、缓存命中、去重融合、权限短路和无候选拒答。

建议后续 Spec 明确以下文件影响范围：

- 新增查询改写相关服务文件。
- 新增或调整增强检索相关服务文件。
- 调整配置对象中的查询改写参数。
- 调整依赖组装或路由工厂，使查询管道可选择增强版本。
- 新增查询改写、增强检索和查询服务接入测试。

## 1.6 验收方向

本 Plan 不直接修改代码，但后续 Spec 和实现应能验证以下行为：

- 有读权限用户发起查询时，系统保留原始问题并按配置执行 HyDE 和多路扩展。
- 任一知识库无读权限时，请求在入口层失败，不触发 HyDE、多路扩展、向量化、全文检索或生成。
- HyDE 成功时，它只参与检索，不进入最终答案或 sources。
- 多路扩展成功时，扩展问题数量不超过配置上限，且与原始问题重复的内容会被去掉。
- HyDE 失败时，系统继续使用原始问题和可用的扩展问题检索。
- 多路扩展失败时，系统继续使用原始问题和可用的 HyDE 文本检索。
- HyDE 和多路扩展都失败时，系统回退到原始问题混合检索。
- Redis 缓存读取或写入失败时，查询主流程不失败。
- 改写后的所有检索都包含同一权限范围、当前文档版本、已完成索引状态和未删除过滤。
- 同一个 chunk 被原始问题、HyDE 或扩展问题多路召回时，最终 sources 中只出现一次。
- 无任何有效候选时返回固定拒答，不调用聊天模型。
- 正常响应中的 hit_count 与实际返回 sources 数量一致，用户不可见 HyDE 假设文本。
- 日志能区分改写耗时、缓存命中、各路召回数量、融合候选数量和降级原因。
- 文档文件名符合 Plan 阶段要求，使用 -plan.md 后缀。
