# 01-技术栈

本文对齐 `docs/references/01-rag-kb项目介绍.md` 中的 Spring AI 版技术栈，给出 LangChain/Python 重构后的推荐技术栈。原则是：能保留的基础设施尽量保留，框架层从 Java/Spring AI 切换到 Python/FastAPI/LangChain，不适合直接替换的能力用 Python 生态中的等价组件补齐。

## 技术栈对比

| 层次 | 原 Spring AI 技术 | LangChain 重构技术 | 对齐说明 |
| --- | --- | --- | --- |
| AI 框架 | Spring AI 1.1.x | LangChain Python | 承接 Chat Model、Embedding、Document Loader、Text Splitter、Retriever、Tool/Agent 等能力。 |
| 工作流编排 | Spring Service 手写管道 | 显式 Service 编排，复杂状态流可用 LangGraph | RAG 管道仍建议手写关键步骤，避免一行式抽象掩盖权限、降级和引用溯源。 |
| 大模型 | 通义千问 `qwen-plus` | `langchain_openai.ChatOpenAI` + DashScope OpenAI-compatible endpoint | DashScope 提供 OpenAI 兼容模式，可用 OpenAI 风格客户端接入。 |
| Embedding | `text-embedding-v3` | `langchain_openai.OpenAIEmbeddings` + DashScope OpenAI-compatible endpoint | 保留中文 embedding 模型；建库和查询必须使用同一模型。 |
| Reranker | `gte-rerank` | 自定义 `RerankerService` 调 DashScope Rerank API | LangChain 不应强行包办精排；项目需要显式超时和降级。 |
| 后端框架 | Spring Boot 3.5.x / Java 21 | FastAPI / Python 3.12 | Python 生态更适合 LangChain、RAGAS 和模型实验。 |
| API 文档 | SpringDoc / Actuator | FastAPI OpenAPI / `/docs` | FastAPI 原生生成 OpenAPI 文档。 |
| 异步任务 | Spring `@Async` / 线程池 | FastAPI BackgroundTasks、Celery 或 Dramatiq | 初期可用 BackgroundTasks；生产建议 Celery/Dramatiq + Redis。 |
| 向量数据库 | PostgreSQL + PGVector | PostgreSQL + PGVector + `langchain-postgres` | 保留原选型，便于业务表、权限过滤、全文检索和向量检索共库实现。 |
| 关系数据库 | PostgreSQL | PostgreSQL | 继续承载知识库、文档、chunk、索引任务、权限、对话记录。 |
| ORM / SQL | Spring Data JPA / Hibernate Vector | SQLAlchemy 2.x + Alembic + 必要时原生 SQL | PGVector 相似度、全文检索、RRF 融合可直接写 SQL，避免 ORM 过度抽象。 |
| 全文检索 | PostgreSQL Full Text Search | PostgreSQL Full Text Search | 保留，与向量检索组成混合检索。中文分词可按需要接入 `zhparser` 或外部分词方案。 |
| 缓存 | Redis 7.x | Redis 7.x + `redis.asyncio` | 用于 embedding 缓存、查询缓存、索引任务进度和限流。 |
| 文件存储 | MinIO | MinIO + Python `minio` SDK | 保留原始文档永久存储方案。 |
| 文档解析 | PDFBox / POI / Flexmark | LangChain loaders + PyPDF / python-docx / Markdown 解析库 | LangChain loader 可做入口，但要统一补充页码、章节、文件名等来源元数据。 |
| 分块 | 自定义 ChunkSplitter | `RecursiveCharacterTextSplitter` + 自定义语义分块策略 | 初期使用递归字符分块；后续按 Markdown 标题、页码、语义边界增强。 |
| Token 计数 | jtokkit | `tiktoken` 或模型兼容 tokenizer | 用于上下文裁剪和成本估算；若 DashScope 模型 token 规则不同，应预留适配层。 |
| 权限认证 | Sa-Token | FastAPI JWT + RBAC 依赖 | Sa-Token 是 Java 生态组件，Python 侧替换为 JWT、依赖注入和数据库权限校验。 |
| 权限隔离 | 拦截器 + SQL 硬过滤 | FastAPI dependency + Repository SQL 硬过滤 | 关键原则不变：检索层必须带 `tenant_id` / `kb_id` 权限条件。 |
| 前端 | React | React | 保留。后端 API 改为 FastAPI 风格即可。 |
| 流式输出 | Spring SSE | FastAPI `StreamingResponse` / SSE | 用于模型流式 token、引用信息和任务状态推送。 |
| 部署 | Docker Compose | Docker Compose | 保留，一键拉起 PostgreSQL、Redis、MinIO、后端和前端。 |
| 监控 | Micrometer + Grafana | Prometheus metrics + Grafana | Python 侧统一使用 OpenTelemetry API 记录指标，经 OpenTelemetry Prometheus exporter 从 `/metrics` 暴露。 |
| 日志链路 | SLF4J + MDC traceId | `structlog` / 标准 logging + request id | 保留 trace id，记录检索耗时、模型耗时、token 成本和降级事件。 |
| 评估 | RAGAS 框架 | RAGAS | RAGAS 原生 Python，重构后更直接。 |
| 测试 | JUnit / Spring Boot Test | pytest + pytest-asyncio | 覆盖服务层、权限过滤、检索排序、降级和 API。 |
| 代码质量 | Maven / Checkstyle 可选 | Ruff + mypy | Python 侧建议静态检查和类型检查。 |
| 依赖管理 | Maven | uv | 当前项目已是 Python 工程，使用 `pyproject.toml` 和 uv 管理依赖。 |

## 保留的核心基础设施

以下技术无需因为重构而替换：

- PostgreSQL + PGVector：继续作为关系数据、向量数据和全文检索的统一底座。
- Redis：继续承担缓存、进度、限流和异步任务辅助能力。
- MinIO：继续保存原始文档，数据库只保存对象 key 和元数据。
- React：继续作为文档管理和对话界面前端。
- Docker Compose：继续作为本地开发和演示环境编排方式。
- RAGAS：从 Java 项目接入评估框架，变为 Python 原生集成。

## 必须替换的技术

| 原技术 | 替换原因 | 替代方案 |
| --- | --- | --- |
| Spring AI | Java 生态框架，不适用于 LangChain 重构 | LangChain Python |
| Spring Boot | 后端语言和框架切换到 Python | FastAPI |
| Sa-Token | Java 权限框架 | JWT + FastAPI dependencies + RBAC |
| Micrometer | Java 监控体系 | OpenTelemetry Python + Prometheus exporter |
| PDFBox / POI / Flexmark | Java 文档解析库 | PyPDF、python-docx、Markdown/Unstructured/LangChain loaders |
| jtokkit | Java tokenizer | tiktoken 或模型适配 tokenizer |
| Spring Retry / `@Async` | Spring 机制 | tenacity、Celery/Dramatiq、asyncio |

## LangChain 设计取舍

LangChain 提供 RAG 组件，但本项目不能简单使用“向量库 + retriever + prompt”的最小链路替代参考项目。推荐使用方式如下：

1. 文档加载、分块、embedding、基础向量存取可以使用 LangChain 集成。
2. 混合检索、权限过滤、RRF、Reranker、上下文裁剪、引用溯源应保持项目自有服务。
3. 基础问答优先使用显式 `RagQueryService` 编排，而不是完全交给 Agent 自主调用。
4. Agent 可作为增强层，例如“跨文档对比”“多轮诊断”“管理型操作助手”，但底层检索工具必须遵守权限和引用规则。

## 初始架构建议

```plain
FastAPI API 层
  -> Auth / Permission dependency
  -> DocumentService / IndexService
  -> RagQueryService
      -> QueryRewriter
      -> HybridRetriever
          -> PGVector search
          -> PostgreSQL full text search
      -> RrfFusion
      -> RerankerService
      -> ContextTrimmer
      -> SourceBuilder
      -> ChatModel client
  -> StreamingResponse / JSON response
```

## 阶段性落地顺序

1. 项目骨架：FastAPI、配置、数据库连接、健康检查、Docker Compose。
2. 数据模型：知识库、文档、chunk、索引任务、权限、会话记录。
3. 离线索引：MinIO 上传、文档解析、分块、embedding 缓存、PGVector 写入。
4. 基础查询：向量检索、Prompt 组装、模型生成、防幻觉拒答。
5. 混合检索：PostgreSQL 全文检索、RRF 融合、多知识库权限过滤。
6. 精排与裁剪：Reranker、超时降级、Token 预算控制。
7. 引用与流式：引用溯源、SSE、多轮对话。
8. 工程质量：评估流水线、监控指标、Token 成本记录、权限测试。
