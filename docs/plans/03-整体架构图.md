# 03-整体架构图

本文基于 `docs/references/03-技术架构设计.md`，将原 Spring AI / Spring Boot 架构改写为 LangChain / FastAPI / Python 版本。核心架构仍然保持两条管道：**离线索引管道** 和 **在线查询管道**。

## 二、各层职责

### 用户层

前端使用 React，提供文档上传、知识库管理、索引状态查看、自然语言问答、引用来源展示和流式回答展示。

### 接入层

FastAPI Router 替代 Spring Controller：

- `DocumentRouter`：文档上传、删除、重建索引、索引状态查询。
- `KnowledgeBaseRouter`：知识库创建、成员授权、权限配置。
- `ChatRouter`：普通问答、流式问答、多轮会话。
- `AuthRouter`：登录、刷新 token、当前用户信息。
- `HealthRouter` / `MetricsRouter`：健康检查和 Prometheus 指标。

认证和权限通过 FastAPI dependency 完成。认证依赖解析出 `CurrentUser` 后，可以写入 `contextvars.ContextVar`，供 Service、LangChain Tool、Callback、日志链路在同一个异步请求上下文中读取。

`ContextVar` 只负责请求上下文传递，不负责权限安全本身。权限信息仍必须传递到 Service / Repository 层，检索 SQL 必须带上 `tenant_id` / `kb_id` 过滤条件，不能只靠 Prompt 约束模型。请求结束后要 reset 对应 token，避免上下文泄漏到后续请求。

## 三、离线索引管道

离线索引是 RAG 的数据准备链路，应异步执行并记录任务状态。

```plain
上传文档
   -> 保存到 MinIO
   -> 创建 kb_document 记录（status = PENDING）
   -> 创建 index_task 记录
   -> 提交异步索引任务

IndexService
   -> 拉取原始文件
   -> 使用 LangChain Loader / 自定义 Loader 解析文档
   -> 使用 RecursiveCharacterTextSplitter / 自定义策略分块
   -> 补充 chunk 元数据：tenant_id、kb_id、document_id、页码、章节
   -> EmbeddingService 批量向量化，优先命中 Redis 缓存
   -> ChunkRepository 写入 PostgreSQL + PGVector
   -> 更新 document / index_task 状态为 DONE

失败处理
   -> 记录 error_msg 和失败阶段
   -> 自动重试，建议使用指数退避
   -> 支持手动重试和重建索引
```

文档解析可使用 LangChain loaders 作为入口，但业务元数据必须由项目代码统一补齐。分块策略初期可使用递归字符分块，后续再增强 Markdown 标题、页码边界、语义边界等策略。

## 四、在线查询管道

在线查询链路直接影响用户体验，目标是保留原架构中的混合检索、RRF、Reranker、Token 裁剪和引用溯源。

```plain
用户提问
   ↓
① Auth / Permission dependency
   └── 解析当前用户、租户、角色和允许访问的 kb_id 列表
   ↓
② QueryRewriteService
   ├── 标准化用户问题
   ├── HyDE：生成假设性答案用于检索
   └── 多路查询：扩展成多个角度的检索 query
   ↓
③ HybridRetriever
   ├── 向量检索：PGVector TopK
   ├── 全文检索：PostgreSQL Full Text Search TopK
   └── 所有检索 SQL 必须包含 tenant_id / kb_id 权限过滤
   ↓
④ RrfFusionService
   └── 多路结果合并、去重、按 RRF 分数排序
   ↓
⑤ RerankerService
   ├── 调用 DashScope gte-rerank API 精排
   └── 超时或失败时降级：直接使用 RRF TopN
   ↓
⑥ ContextTrimmer
   ├── 按 Token 预算裁剪上下文
   └── 过滤低置信度 chunk
   ↓
⑦ SourceBuilder
   └── 组装引用来源：文档名、页码、章节、chunk_id
   ↓
⑧ RagQueryService
   ├── 构造 Prompt
   ├── ChatOpenAI 调用 qwen-plus
   ├── 知识库无结果时拒答
   └── HTTP / SSE 返回答案和引用
```

基础问答链路优先使用显式服务编排，不建议完全交给 Agent 自主决定是否检索。LangChain Agent 可以作为增强层，用于跨文档对比、多轮诊断或管理型助手，但底层检索工具必须复用同一套权限过滤和引用溯源逻辑。

## 五、关键选型说明

### PGVector 继续作为主向量库

PGVector 和业务数据同在 PostgreSQL 中，适合本项目的多租户权限过滤、全文检索融合和事务一致性需求。百万级向量规模内优先使用 PGVector；当向量规模达到千万级以上，再评估迁移 Qdrant / Milvus。

### LangChain 只做合适的抽象

LangChain 用于模型、Embedding、Loader、Splitter、基础向量存取和工具封装。以下逻辑保持项目自有实现：

- 权限过滤。
- 混合检索 SQL。
- RRF 融合。
- Reranker 超时降级。
- Token 预算裁剪。
- 引用溯源。
- 防幻觉拒答。
- 评估与成本统计。

### 查询延迟目标

参考原架构目标，在线查询 TTFT 目标仍为 3 秒内：

```plain
查询改写（LLM 调用）       ~800ms
向量检索（PGVector）       ~50ms
全文检索（PostgreSQL）     ~30ms
RRF 融合                  ~5ms
Reranker API              ~300ms（超时阈值建议 800ms）
上下文裁剪                 ~5ms
模型首 Token              ~600ms
────────────────────────────
正常路径 TTFT              ~1800ms
Reranker 降级路径          ~1500ms
```

## 六、模块映射

| 原 Spring AI 模块 | LangChain 重构模块 |
| --- | --- |
| Controller | FastAPI Router |
| Sa-Token 拦截器 | JWT dependency + RBAC dependency |
| UserContext ThreadLocal | `contextvars.ContextVar[CurrentUser]` |
| IndexTaskExecutor | BackgroundTasks，生产可替换 Celery / Dramatiq |
| DocumentLoader | LangChain loaders + 自定义 Loader |
| ChunkSplitter | `RecursiveCharacterTextSplitter` + 自定义分块策略 |
| EmbeddingService | `OpenAIEmbeddings` + Redis 缓存 |
| ChatClient | `ChatOpenAI` |
| WebFlux Reranker 调用 | `httpx` + `RerankerService` |
| Repository | SQLAlchemy Repository + 原生 SQL |
| Actuator / Micrometer | FastAPI health + Prometheus metrics |
