# 05-索引管道建立与流程打通

本文基于 `docs/references/09-Embedding 服务——批量向量化与缓存.md`，整理 LangChain / FastAPI 版本中离线索引管道的建立计划，目标是帮助理解“上传文档后如何一步步变成可检索 chunk”的项目流程。

需要特别说明：`app/services/embedding.py` 已经完成，本计划不再规划 Embedding 向量化模块的代码实现，也不重复设计缓存、批处理、重试、向量序列化等内部细节。本文只把 Embedding 服务当作索引管道中的已完成依赖，说明它如何与上下游衔接。

本阶段也不实现路由层。`docs/references/09-Embedding 服务——批量向量化与缓存.md` 中有些接口或类只是为了说明索引流程而给出方法签名或简化占位，例如上传接口、状态查询接口、部分 Repository 方法、`MinioStorageService` 简化服务和开发数据初始化入口。它们可以作为下一阶段设计参考，但不作为本阶段必须完成的代码范围。

## 一、In Scope 与 Out of Scope

In scope：

- 建立离线索引管道的整体流程：文档记录、索引任务、异步执行、解析、分块、向量化衔接、chunk 入库、状态更新。
- 规划 `IndexService` / Repository 等服务层和仓储层模块边界。
- 规划索引任务状态流：`PENDING -> RUNNING -> DONE / FAILED`。
- 规划文档状态流：`PENDING -> PROCESSING -> DONE / FAILED`。
- 规划重建索引的版本策略：新版本写完后再清理旧版本。
- 规划失败记录、可重试任务、手动重试和状态查询。
- 规划开发环境测试数据如何跑通完整管道。
- 给出与当前 Python 代码结构对齐的落地顺序和验证方式。

Out of scope：

- 不实现或重写 Embedding 服务代码。
- 不设计 Embedding Redis 缓存内部结构。
- 不实现 FastAPI 路由层，包括上传接口、文档详情接口、索引状态查询接口和手动重试接口。
- 不实现参考文档中只给出方法签名或简化占位的接口/类；这些内容进入下一阶段。
- 不实现 `MinioStorageService` 的完整上传、下载、删除、bucket 管理和线程池封装；本阶段只保留让 `IndexService` 能依赖的最小接口签名。
- 不实现在线查询管道中的混合检索、RRF、Reranker、上下文裁剪和回答生成。
- 不实现完整 RBAC 权限系统，但索引相关查询和后续检索必须保留 `kb_id` / `tenant_id` 过滤意识。
- 不引入 Celery / Dramatiq 等生产级任务队列作为第一阶段必选项；先以项目当前 FastAPI 结构打通流程，后续再替换任务执行器。

## 二、当前项目基础

当前项目已经具备以下基础：

```plain

  -> KnowledgeBase / KbDocument / DocChunk / IndexTask 等 SQLAlchemy 模型

app/db/schema.sql
  -> PostgreSQL 表结构、PGVector 扩展、chunk 向量字段、全文检索触发器

app/services/document_loader/
  -> 多格式文档加载与解析服务

app/services/chunking.py
  -> 文档分块服务

  -> 已完成的批量向量化与 Redis 缓存服务

tests/resources/test-docs/
  -> 开发环境样本文档
```

因此下一步的重点不是再做单点能力，而是把已有能力串成一条可观察、可重试、可验证的索引链路。

## 三、目标索引流程

目标流程如下：

```plain
准备文档记录
  -> 由测试、脚本或下一阶段路由层创建 kb_document
  -> kb_document 已包含 doc_id / kb_id / minio_path / file_name
  -> 原始文件已保存到 MinIO 或测试存储

IndexService.submit_index_task(doc_id)
  -> 创建 kb_index_task 记录，status = PENDING
  -> 提交异步索引任务

IndexService._launch_task(task_id, doc_id)
  -> 在后台启动 IndexService.run_task(...)
  -> 本阶段可用 asyncio.create_task(...) 做本地投递

IndexService
  -> 更新 task = RUNNING，document = PROCESSING
  -> 从 MinIO 下载原始文件
  -> DocumentLoaderService 解析文档
  -> ChunkingService 分块并保留来源元数据
  -> EmbeddingService 批量生成向量
  -> 组装 DocChunk 记录
  -> 批量写入 PostgreSQL + PGVector
  -> 删除旧版本 chunk
  -> 更新 document = DONE，task = DONE

失败路径
  -> 记录 error_msg、失败阶段、finished_at
  -> document = FAILED，task = FAILED
  -> 可重试错误进入指数退避重试
  -> 达到上限后等待人工手动重试
```

这条管道要达到三个结果：

1. `IndexService.submit_index_task(...)` 可以快速返回，不同步等待解析和向量化。
2. 数据库中的文档和任务状态可被读取，下一阶段路由层可以据此提供状态查询。
3. 任意阶段失败都不会悄悄写入脏向量，也不会让旧版本知识在重建中断档。

下一阶段实现上传接口时，如果上传、权限校验、MinIO 完整存储、文档记录创建逻辑开始变复杂，再考虑新增 `DocumentService` 承接“上传与文档管理”职责。

### 3. MinioStorageService

### 5. 后台投递

本阶段不单独新增 `IndexTaskLauncher`。

原因：

- 参考文献中的 `IndexTaskLauncher` 主要为了解决 Spring `@Async` 自调用代理问题。
- Python / FastAPI 没有这个 Spring AOP 自调用问题。
- 当前阶段不考虑后续任务队列扩展，单独抽模块会增加理解成本。

建议把投递逻辑收敛在 `IndexService` 内部私有方法：

```python
def _launch_task(self, task_id: int, doc_id: int) -> None:
    asyncio.create_task(self.run_task(task_id, doc_id))
```

后续如果需要接 Celery / Dramatiq，再重新抽 `TaskDispatcher` 或 `IndexTaskLauncher`。

### 6. IndexService

建议新增：

```plain
app/services/indexing.py
```

职责：

- 作为离线索引管道核心编排器。

- 调用分块服务生成 chunk。

- 不重新实现 embedding 缓存。
- 不直接处理 HTTP 请求。
- 不做 Prompt 或回答生成。
- 不依赖前端上传文件的临时内存对象完成可重试任务。

## 五、核心状态与版本策略

### 索引任务状态

`kb_index_task.status`：

```plain
PENDING
  -> RUNNING
  -> DONE
  -> FAILED
```

关键字段：

- `retry_count`：当前已重试次数。
- `max_retry`：最大重试次数，默认 3。
- `error_msg`：失败原因。
- `started_at`：开始时间。
- `finished_at`：结束时间。

### 文档状态

`kb_document.status`：

```plain
PENDING
  -> PROCESSING
  -> DONE
  -> FAILED
```

关键字段：

- `chunk_count`：本次索引成功后的 chunk 数。
- `token_count`：chunk token 估算或 embedding 统计。
- `version`：当前可检索版本。
- `indexed_at`：最近一次索引完成时间。
- `error_msg`：最近一次失败原因。

### 重建索引版本策略

重建索引必须遵守“先写新版本，再删旧版本”：

```plain
读取当前 document.version
  -> new_version = old_version + 1
  -> 新 chunk 写入 doc_version = new_version
  -> 所有新 chunk 写入成功
  -> 更新 document.version = new_version，status = DONE
  -> 删除 doc_version < new_version 的旧 chunk
```

这个策略避免两类生产问题：

- 先删旧版本再写新版本，如果写入失败，用户查询会直接断档。
- 新旧 chunk 混在一起时，后续检索必须只召回当前版本 chunk。

实现时可以根据事务边界选择“先更新 document.version 再写 chunk”或“写完 chunk 后再更新 document.version”。无论哪种方式，查询 SQL 都必须能过滤到稳定的当前版本，避免召回半新半旧的数据。

## 六、分阶段落地计划

### 阶段 1：Repository 和状态更新能力

目标：先让数据库读写边界清楚。

计划：

- 新增 `DocumentRepository`，支持创建、按 ID 查询、更新状态、更新索引结果。
- 新增 `IndexTaskRepository`，支持创建任务、更新状态、记录失败、查询最近任务。
- 新增 `ChunkRepository`，支持批量插入 chunk、按文档和版本清理旧 chunk。
- 补充 repository 单元测试或轻量集成测试。

验收：

- 能创建一条 `KbDocument` 和一条 `IndexTask`。
- 能把 task 从 `PENDING` 更新到 `RUNNING` / `DONE` / `FAILED`。
- 能批量写入 chunk 并按 `doc_id + doc_version` 清理旧版本。

### 阶段 2：IndexService 依赖准备

目标：补齐 `IndexService` 执行前需要依赖的仓储和存储签名。文档记录创建由测试、脚本或下一阶段上传流程负责；本阶段不新增 `DocumentService`。

计划：

- 新增 `MinioStorageService` 最小接口签名，至少包含 `download(object_key) -> bytes`。
- 确认 `KbDocumentRepository` 能按 `doc_id` 读取文档元数据。
- 确认 `IndexTaskRepository` 能创建 `IndexTask(status=PENDING)`。
- 测试中可直接创建 `KbDocument` 记录，并使用 fake storage 返回样本文档内容。

验收：

- 测试或脚本能先准备一条包含 `minio_path` 的 `kb_document`。
- `IndexService.submit_index_task(doc_id)` 能创建对应 `kb_index_task`。
- 此阶段不读取文件内容、不解析、不分块、不写入 chunk。

### 阶段 3：IndexService 串联已有能力

目标：真正打通解析、分块、embedding、入库。

计划：

- 新增 `IndexService.run_task(task_id, doc_id)`。
- 任务开始时更新 `task=RUNNING`、`document=PROCESSING`。
- 通过 `MinioStorageService.download(...)` 读取文件内容；本阶段可由 fake storage 提供 bytes。
- 调用 `DocumentLoaderService` 解析。
- 调用 `ChunkingService` 分块。
- 调用已完成的 `EmbeddingService.embed_documents(texts)`。
- 按下标把 chunk 和 vector 组装为 `DocChunk`。
- 分批写入 `kb_doc_chunk`。
- 更新文档统计和任务状态。

验收：

- 样本文档能从 `PENDING` 进入 `DONE`。
- `kb_doc_chunk` 中能看到对应 chunk 和 1024 维向量。
- chunk 的 `doc_id`、`kb_id`、`chunk_index`、`page_num`、`section_title`、`doc_version` 保留正确。
- embedding 失败时不写入零向量，任务进入 `FAILED`。

### 阶段 4：异步任务投递与数据库状态可读

目标：`IndexService.submit_index_task(...)` 快速返回，后台执行索引；HTTP 状态查询接口下一阶段实现。

计划：

- 在 `IndexService.submit_index_task(...)` 中通过内部 `_launch_task(...)` 投递任务，而不是同步运行完整索引。
- 保证 `KbDocument` 和 `IndexTask` 状态字段可被 Repository 查询。
- 日志中记录 `doc_id`、`task_id`、`kb_id`、耗时和失败阶段。

验收：

- `submit_index_task(...)` 能在索引完成前返回。
- 后台任务继续执行索引。
- 测试可以通过 Repository 读取任务状态。
- 任务完成后文档状态变为 `DONE`。

### 阶段 5：失败分类与重试

目标：让临时失败可以恢复，永久失败可观察。

计划：

- 明确失败阶段：文档不存在、MinIO 下载失败、解析失败、分块为空、Embedding 失败、DB 写入失败。
- 对可重试失败增加指数退避。
- 对不可重试失败直接进入 `FAILED`。
- 保留手动重试所需的服务层方法或任务创建能力；HTTP 接口下一阶段实现。

建议分类：

| 失败类型 | 是否自动重试 | 原因 |
| --- | --- | --- |
| 文档记录不存在 | 否 | 重试也找不到数据 |
| MinIO 临时网络错误 | 是 | 可能恢复 |
| MinIO 对象不存在 | 否 | 数据不一致，需要人工处理 |
| 解析失败 | 视错误而定 | 文件损坏通常不可恢复，解析服务抖动可恢复 |
| 分块为空 | 否 | 文档无有效文本 |
| Embedding 临时失败 | 是 | 下游服务可能恢复 |
| Embedding 4xx 配置错误 | 否 | 重试无意义 |
| DB 写入临时错误 | 是 | 连接抖动可能恢复 |

延迟重试机制参考原实现：

```plain
索引任务失败
  -> task.retry_count + 1
  -> task.status 改回 PENDING
  -> delay_seconds = 2 ** (retry_count - 1)
  -> 不在索引执行线程中 sleep
  -> 通过独立调度器等待 delay_seconds
  -> 到期后调用 IndexService._launch_task(...) 重新投递任务
```

这里的关键点是：失败任务等待重试时，不占用真正执行索引的工作线程。索引线程只负责解析、分块、向量化、写库等实际工作；延迟等待交给独立调度器。调度时间到了以后，再通过 `IndexService._launch_task(...)` 把任务放回索引执行入口。

只有持久化来源的 MinIO 任务支持自动重试。因为 MinIO 任务失败后还能通过 `kb_document.minio_path` 重新读取原始文件。内存文本任务不自动重试，因为文本内容只存在于当次方法调用内存中，没有持久化到数据库或 MinIO，延迟重试时无法可靠恢复原始文本。

验收：

- 自动重试不阻塞索引执行线程。
- 达到最大重试次数后任务保持 `FAILED` 并记录错误。
- 服务层手动重试入口会创建新的 `REINDEX` 任务或重置失败任务，二者选其一并保持一致。

### 阶段 6：重建索引和旧版本清理

目标：在服务层支持文档更新和重建索引，不影响查询可用性；HTTP 触发接口下一阶段实现。

计划：

- 服务层 `reindex_document(doc_id)` 或等价方法创建 `REINDEX` 任务。
- 重建时递增版本号。
- 新版本 chunk 全部写入成功后清理旧版本 chunk。
- 检索 SQL 后续必须按 `doc_version = kb_document.version` 或等价条件过滤当前版本。

验收：

- 同一个文档重建后，只保留当前版本可被查询。
- 重建失败时，不破坏旧版本 chunk。
- 清理旧版本失败时，不影响新版本可用，但需要记录告警并可再次清理。

### 阶段 7：开发样本数据跑通

目标：用固定样本文档验证完整索引管道。

计划：

- 使用 `tests/resources/test-docs/hr-handbook.txt`。
- 使用 `tests/resources/test-docs/tech-spec.txt`。
- 使用 `tests/resources/test-docs/product-faq.txt`。
- 在本地环境创建对应知识库和文档。
- 触发后台索引任务。
- 用测试等待任务完成并断言 chunk 数。

验收：

- 至少 3 份测试文档进入 `DONE`。
- chunk 总数大于 0。
- 每个 chunk 都有 `kb_id`、`doc_id`、`chunk_index` 和向量。
- 重复运行不会无限重复插入样本文档。

## 七、与 Embedding 服务的衔接点

Embedding 服务已完成，索引管道只需要遵守以下调用约束：

```python
texts = [chunk.page_content for chunk in chunks]
vectors = await embedding_service.embed_documents(texts)
```

索引服务必须保证：

- `texts` 的顺序与 `chunks` 的顺序一致。
- `vectors` 的数量必须等于 `chunks` 的数量。
- 第 `i` 个向量写入第 `i` 个 chunk。
- Embedding 抛错时，当前索引任务失败，不写入零向量。
- Embedding 服务不接收 `kb_id`、`doc_id`、权限信息；这些字段在 `DocChunk` 入库时补齐。

需要记录但不在本计划实现的细节：

- Embedding cache hit / miss 属于 `EmbeddingService` 内部指标。
- 索引任务可以记录本次 chunk 数、耗时和 token 估算。
- 后续监控章节再统一接入 Prometheus 指标。

## 九、流程理解图

下面用一份文档的生命周期串起来：

```plain
1. 准备文档记录
   test/script/next-stage API -> MinIO object + kb_document(PENDING)

2. 建任务
   IndexService.submit_index_task(doc_id) -> kb_index_task(PENDING)

3. 投递后台任务
   IndexService._launch_task(...) -> IndexService.run_task(...)

4. 开始执行
   task(RUNNING), document(PROCESSING)

5. 读取原文
   MinIO object -> bytes / stream

6. 解析
   DocumentLoaderService -> list[Document] 或统一 ParseResult

7. 分块
   ChunkingService -> list[Document chunk]

8. 向量化
   EmbeddingService -> list[list[float]]

9. 入库
   ChunkRepository.bulk_insert(DocChunk[])

10. 收尾
   clean old versions
   document(DONE, chunk_count, token_count, indexed_at)
   task(DONE, finished_at)
```

失败路径可以理解为：

```plain
任何阶段抛错
  -> 捕获错误
  -> 记录失败阶段和 error_msg
  -> task = FAILED
  -> document = FAILED
  -> 如果可重试且 retry_count < max_retry
       -> 延迟重新投递
     否则
       -> 等待人工查看和手动重试
```

## 十、关键风险与取舍

### 1. 后台任务方案

第一阶段用 FastAPI 本地后台任务或 `asyncio.create_task(...)` 更简单，但进程重启会丢失正在执行的内存任务。生产环境应迁移到 Celery / Dramatiq，并让任务从数据库恢复状态。

计划取舍：

- 第一阶段先打通流程。
- 当前阶段不抽 `IndexTaskLauncher`，投递逻辑放在 `IndexService._launch_task(...)`。
- 后续确实需要任务队列时，再抽 `TaskDispatcher` 或 `IndexTaskLauncher`。

### 2. MinIO SDK 同步阻塞

Python MinIO SDK 是同步接口。直接在 async 路径中下载大文件可能阻塞事件循环。

计划取舍：

- 本阶段只定义 `MinioStorageService` 签名，不处理同步 SDK 阻塞问题。
- 下一阶段实现完整 MinIO 服务时，对大文件下载统一放入线程池。

### 3. 版本切换窗口

重建索引期间如果过早更新 `document.version`，查询可能看不到尚未写完的新版本；如果过晚更新，旧版本仍可查但新版本不可见。

计划取舍：

- 第一阶段查询链路尚未完成时，先确保写入顺序和清理顺序正确。
- 后续实现检索 SQL 时，必须明确当前版本过滤逻辑。

### 4. 失败后部分数据残留

如果新版本 chunk 已写入一部分后失败，会留下未完成版本数据。

计划取舍：

- 查询只看 `document.version` 对应版本，避免召回未完成版本。
- 重试时生成新版本或先清理同版本未完成 chunk，二者选定一种策略后保持一致。

### 5. 权限字段不足

当前 `DocChunk` 中有 `kb_id`，但没有显式 `tenant_id`。如果后续多租户设计引入 `tenant_id`，索引管道需要在 `KbDocument` 和 `DocChunk` 写入时同步补齐。

计划取舍：

- 现阶段先按 `kb_id` 和知识库权限表过滤。
- 多租户租户字段补齐时，应同步更新模型、schema、索引入库和检索 SQL。

## 十一、推荐实施顺序

本阶段建议按以下顺序推进：

1. Repository：先把 `KbDocument`、`IndexTask`、`DocChunk` 的数据库操作封装清楚。
2. MinioStorageService：定义最小 `download(...)` 接口签名，并准备测试 fake。
3. IndexService：完成内部 `_launch_task(...)` 后台投递方法。
4. IndexService：完成 `submit_index_task(doc_id)`，创建 `IndexTask` 并通过 `_launch_task(...)` 投递后台任务。
5. IndexService：串联 loader、chunking、embedding、chunk 入库。
6. 状态读取：通过 Repository 读取文档和任务状态，供测试验证。
7. 失败重试：补齐自动重试和手动重试。
8. 重建索引：补齐版本策略和旧版本清理。
9. Dev seed：用样本文档跑通完整链路。
10. 监控与日志：记录耗时、chunk 数、失败阶段、token 估算。

下一阶段再推进：

1. Document API：上传、文档详情、索引状态查询、手动重试、重建索引。
2. MinioStorageService 完整实现：上传、下载、删除、bucket 管理、object key 生成和同步 SDK 线程池封装。
3. Schema：请求和响应模型。
4. 权限依赖：上传和重建索引前校验知识库写权限。
5. 前端联调：文档上传后展示索引进度。

这一路线的核心是先把“单文档成功索引”跑通，再逐步补可观测、重试和重建能力。不要一开始就把任务队列、监控、权限、评估全部塞进同一个改动里。
