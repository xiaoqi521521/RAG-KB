前面 RAG 模块带大家把 RAG 的每个零件都学了一遍——Embedding、分块、PGVector、混合检索、Reranker、效果评估……但鸡哥知道很多同学学完有个感觉：**单个技术点能跟着跑，但让你现在出去独立搭一个企业级 RAG 系统，你能搞定吗？**

文档加载怎么处理多格式？分块策略参数怎么选？向量写入失败怎么重试？混合检索 RRF 怎么融合？Reranker 超时了怎么降级？引用溯源怎么实现？多租户怎么隔离？……

这些问题，其他人的 Demo 里都没有。这个项目实战专门解决这个问题——不是又一个跑通就结束的 Demo，而是按企业级标准设计的完整系统：有异常处理、有降级策略、有权限隔离、有效果评估，每一个模块都是生产可用的。

## 一、这个项目做什么
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175229602-e3cfb759-0df1-4e53-84bc-1a0b671b63a8.png" width="1111" title="" crop="0,0,1,1" id="udc8999b8" class="ne-image">

**jc-rag-kb：鸡翅知识库问答系统**

场景是这样的：公司内部有大量文档——产品手册、技术规范、操作流程、制度文件、FAQ……这些文档散落在各处，员工每次要找什么信息，要么在内网搜关键词（搜出来一堆不相关的），要么直接问同事（占用别人时间）。

有了这个系统之后：

员工上传文档，系统自动解析、分块、向量化，建立索引。员工有问题，直接用自然语言问，系统给出精准回答，并标注答案来自哪个文档的哪个位置。

## 二、能做到什么程度
先看效果，再讲技术。

### 问答精准，答案来源透明
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175242097-0e9f7baf-166b-4e7b-87fb-2f2492bf973e.png" width="1094" title="" crop="0,0,1,1" id="uc6d45f85" class="ne-image">

不是那种"我根据我的理解给你讲一下"的回答方式，而是**每一句话都有文档出处**，精确到哪个文件、哪一章、哪一页。

```plain
用户："新员工入职第一天需要做哪些事情？"

系统："根据《员工手册 v2.3》第三章，入职第一天需要完成以下步骤：

      1. 8:30 前往行政部前台，凭录用通知书领取工牌和电脑
      2. 按照《开发环境配置指南》完成 VPN 和开发环境搭建
      3. 与直属 Leader 进行 30 分钟入职对齐会
      4. 在 HR 系统签字确认《代码规范文档》

      📎 来源：员工手册v2.3.pdf · 第3章入职流程 · 第12页
      📎 来源：开发环境配置指南.md · 第1节快速开始"
```

答案从哪来、出自哪个文件、对应哪一节，一清二楚。用户可以直接点进去核实原文。

### 跨文档对比，发现矛盾不遗漏
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175258206-6f5aecc9-e438-463e-86f1-dc73320d89de.png" width="1103" title="" crop="0,0,1,1" id="u98ac088f" class="ne-image">

两份文档说法不一致？系统能发现，还会指出差异在哪。

```plain
用户："技术规范和产品手册对 API 限流的规定一样吗？"

系统："两份文档对限流的规定存在出入，具体如下：

      《技术规范 v1.4》：单用户每分钟 100 次，采用滑动窗口
      《产品手册 Q4》：每个 API Key 每分钟 60 次，采用固定窗口

      差异点有两处：一是调用次数上限不同（100 vs 60），
      二是计算方式不同（滑动窗口 vs 固定窗口）。

      建议以技术规范为准，产品手册可能未同步最新修订。

      📎 技术规范v1.4.pdf · 第5章 · API 限流策略
      📎 产品手册Q4.pdf · 第8章 · 接口调用说明"
```

这种查询靠人工排查要花不少时间，系统秒级给出。

### 知识库没有的，绝不瞎编
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175249975-f22f8563-a5f0-498a-9180-85350256d9cc.png" width="1101" title="" crop="0,0,1,1" id="ufcebc1b5" class="ne-image">

这一点比「能回答」更重要。大模型本身装了很多通用知识，如果不加控制，它会用自己的知识"补"出一个看起来合理但实际不对的答案。

这个系统做了专门设计，**知识库里没有的内容，系统不会猜、不会编**。

```plain
用户："公司对员工副业有什么规定？"

系统："在现有的知识库文档中，未找到关于员工副业规定的相关内容。

      建议您：
      1. 确认《员工手册》是否有最新版本，如有请上传后重新查询
      2. 直接联系 HR 部门获取准确说法

      ⚠️ 我不会用通用知识推测公司政策，以免提供不准确的信息。"
```

### 多部门数据严格隔离，越权查询直接拦截
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175266952-43698560-6e7b-4bb1-ad40-32123b6e26a8.png" width="1109" title="" crop="0,0,1,1" id="u69acbcfc" class="ne-image">

```plain
技术部员工  →  只能查技术知识库，查不到 HR 文档
HR 员工     →  只能查 HR 知识库，查不到技术规范
管理员      →  可跨部门查询所有知识库
```

权限不是靠 Prompt 里说"你只能查 XX 部门的文档"——那种做法不可靠，模型行为不可预测。这个项目的隔离是在**检索层硬过滤**，SQL 查询直接带上 `WHERE kb_id IN (允许的知识库列表)`，跟模型完全解耦，绕不过去。

## 三、为什么要学这个项目
**第一，RAG 是 AI 应用最高频的落地方向之一。**

只要公司有内部文档、私有数据，RAG 就有用武之地。ToB 产品、内部工具、客服系统，大量场景都需要 RAG。而且 RAG 不像 Agent 那样对模型推理能力依赖很强，它的核心在工程——检索质量、分块策略、混合检索、效果评估，这些都是工程侧可以掌控的。

**第二，企业级 RAG 系统的工程复杂度远超 Demo，差距是质的。**

网上的 RAG 教程大多是：上传文件 → SimpleVectorStore → 提问 → 回答，完。这叫 Demo，不叫企业系统。

真正的企业级 RAG 需要面对的是另一个量级的问题：

+ **可靠性**：文档量从几十涨到几万，检索速度和精度还能保持吗？
+ **运维性**：文档更新了怎么增量索引？旧版本怎么管理？索引挂了怎么降级？
+ **安全性**：A 部门的文档能被 B 部门的员工检索到吗？多租户隔离是刚需。
+ **可解释性**：AI 给出的答案来自哪篇文档哪一段？没有引用溯源，业务不敢用。
+ **可度量性**：检索质量怎么量化？Prompt 改了之后是变好了还是变差了？

这个项目把异步索引、文档版本管理、混合检索、Reranker 精排、引用溯源、多租户隔离、效果评估流水线全部覆盖——每一项都是生产环境的真实挑战，不是为了课程凑数。

**第三，可以直接写进简历。**

```plain
"主导设计并实现企业内部知识库 RAG 系统，支持 PDF/Word/Markdown 多格式
文档解析，基于 PGVector + 全文检索的混合检索 + Reranker 精排，
实现引用溯源和防幻觉校验；设计多租户权限隔离方案，
接入 RAGAS 评估框架量化检索质量，系统上线后内部文档检索准确率
达到 85% 以上，人工答疑工单减少 40%"
```

这每一句都有对应的代码和设计可以展开讲。

## 四、RAG 系统的核心难点在哪里
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175338722-d66096fb-6cb9-4b58-8b24-b8d7db070e75.png" width="1108" title="" crop="0,0,1,1" id="ue421aeb9" class="ne-image">

很多人以为 RAG 难在"让模型回答"，其实不是。生成这步模型本身就会，真正的难点在**检索质量**。

```plain
用户问题 → [检索] → 召回的内容 → [生成] → 答案

检索准 → 生成质量有保证
检索不准 → 模型再强也无法正确回答（垃圾进垃圾出）
```

影响检索质量的因素：

<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175345555-5c87077d-b201-488b-b3a7-f1bc0487a272.png" width="1119" title="" crop="0,0,1,1" id="u598f9907" class="ne-image">

1. **分块策略**：块太大，向量语义被稀释；块太小，缺乏上下文
2. **Embedding 模型**：中文场景要选中文专用的
3. **向量检索参数**：TopK 多少、相似度阈值多少
4. **混合检索**：向量检索擅长语义，全文检索擅长精确词，两个互补
5. **Reranker**：召回后精排，把最相关的排到前面
6. **查询改写**：用户问法和文档写法不一样，需要扩展查询

这个项目把上面每一个环节都实现了，而且是企业级的实现——有降级、有评估、有监控。
