## 二、各层职责说明
### 接入层
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175934907-859260d3-68b9-4b45-bc61-2194fcc460f3.png" width="1111" title="" crop="0,0,1,1" id="u6942fb4f" class="ne-image">

+ **Sa-Token**：解析 JWT，把 `userId / departmentId / role` 注入 `UserContext`（ThreadLocal）
+ **权限拦截器**：每个涉及知识库操作的请求，校验当前用户对目标 `kb_id` 是否有权限
+ **限流**：防止单用户滥用问答接口（按 userId 限制 QPS）

### 离线索引管道
这是 RAG 的**数据准备**环节，异步执行，不阻塞用户。

```plain
上传文档
   → 存 MinIO（原始文件永久保存）
   → 创建 KbDocument 记录（status = PENDING）
   → 创建 IndexTask，放入任务队列
   
IndexTaskExecutor（异步线程池）
   → 拉取 PENDING 任务
   → 格式解析（DocumentLoader）
   → 分块（ChunkSplitter）
   → 批量 Embedding（EmbeddingService）
   → 写入 doc_chunk 表（含向量）
   → 更新 KbDocument status = DONE
   
失败处理：
   → status = FAILED，记录 error_msg
   → 支持手动触发重试
   → 自动重试最多 3 次（指数退避）
```

### 在线查询管道
这是用户发问时实时执行的链路，直接影响响应延迟。

```plain
用户提问
   ↓
① 查询改写（QueryRewriter）
   └── 把用户的口语化问题标准化
   └── HyDE：生成假设性回答，用它来检索（效果比原问题好）
   └── 多路查询：扩展成 3 个角度不同的查询
   ↓
② 混合检索（HybridRetriever）
   ├── 向量检索：用 query embedding 在 PGVector 中检索 Top 20
   └── 全文检索：用关键词在 PostgreSQL 全文索引中检索 Top 20
   ↓
③ RRF 融合排序（RrfFusion）
   └── 两路结果合并去重，按 RRF 分数排序
   ↓
④ Reranker 精排（RerankerService）
   ├── 调用 gte-rerank API，对 Top 20 精排
   └── 超时降级：Reranker 超时则用 RRF 分数直接截取 Top 5
   ↓
⑤ 上下文裁剪（ContextTrimmer）
   └── 按 Token 预算裁剪，保证传给模型的 context ≤ 3000 Token
   └── 过低置信度的 chunk 过滤掉
   ↓
⑥ 引用溯源组装（SourceBuilder）
   └── 记录每个 chunk 来自哪个文档、哪页、哪个段落
   ↓
⑦ Prompt 组装 + 生成（ChatClient）
   └── 流式输出（SSE）
   └── 同时推送引用来源信息
```

## 三、关键技术选型说明
### PGVector vs 专用向量库
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175952907-fd46e9c3-5def-4869-bc31-1b19c0cb7b22.png" width="1088" title="" crop="0,0,1,1" id="ud0dd6fee" class="ne-image">

| 对比项 | PGVector | Qdrant/Milvus |
| --- | --- | --- |
| 运维成本 | 低（和业务库同一实例） | 高（独立服务） |
| 混合检索 | 原生支持 SQL JOIN | 需要额外实现 |
| 数据规模 | 百万级向量足够 | 亿级以上 |
| HNSW 索引 | 0.7.0+ 支持 | 成熟 |
| 事务支持 | 完整 ACID | 弱 |


**结论**：百万级数据用 PGVector，超过千万考虑迁移 Qdrant。

### 查询管道各步骤延迟预估
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175958848-395576e4-618d-491f-a47f-3f85bedd3b14.png" width="1125" title="" crop="0,0,1,1" id="ueda3248e" class="ne-image">

```plain
查询改写（LLM调用）     ~800ms
向量检索（PGVector）    ~50ms
全文检索（PG）         ~30ms
RRF 融合              ~5ms
Reranker API          ~300ms（超时阈值 800ms）
上下文裁剪             ~5ms
模型生成首Token        ~600ms
─────────────────────────────
总计 TTFT            ~1800ms（正常路径）
降级路径（Reranker超时）~1500ms
```

目标：TTFT ≤ 3 秒，有充裕余量。

### Spring AI 的 RAG 抽象 vs 自己实现
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175968948-e8d63f3d-93eb-4103-90ca-9e0560482d42.png" width="1099" title="" crop="0,0,1,1" id="ud597fabf" class="ne-image">

Spring AI 提供了 `QuestionAnswerAdvisor`，可以一行接入 RAG。但这个项目不用它，原因：

1. Spring AI 的 RAG 抽象不支持混合检索（只支持向量检索）
2. 不支持 Reranker
3. 不支持引用溯源
4. 无法自定义每个步骤的降级逻辑

所以这个项目**每个步骤自己实现**，Spring AI 只用 `ChatClient`、`EmbeddingModel` 两个组件。这样虽然代码多一点，但每个环节都可以控制和优化。
