## 一、核心用户和使用场景
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175468463-41bf6bac-a90f-46e2-9ed5-c1bcfcbf1614.png" width="1115" title="" crop="0,0,1,1" id="u83110527" class="ne-image">

这个系统有三类用户：

### 普通员工（最主要的用户）
**痛点**：有问题找不到文档，或者找到了但读不完，或者读完了还没找到答案。

**需求**：

+ 用自然语言提问，直接拿到答案
+ 看到答案来源，知道从哪来的（不信任没来源的答案）
+ 支持追问，不用每次重新描述背景
+ 知识库里没有时，系统告诉我"没有"而不是编造

### 知识库管理员
**痛点**：文档更新频繁，手工维护成本高；不知道哪些文档被查得多，哪些没人用。

**需求**：

+ 批量上传文档（PDF/Word/Markdown）
+ 看到文档解析和索引的状态（成功/失败/进行中）
+ 文档更新后一键重建索引
+ 看到查询统计，了解知识库使用情况

### 系统管理员
**需求**：

+ 管理知识库（创建/删除/授权给哪些部门）
+ 查看系统运行状态（Token 消耗、检索耗时、错误率）
+ 跨知识库查询权限配置

## 二、功能模块拆分
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175474130-c9aeee4e-0be8-4632-a116-e6060b2e7a1d.png" width="1102" title="" crop="0,0,1,1" id="u19338745" class="ne-image">

### 2.1 知识库管理
```plain
知识库（KnowledgeBase）
├── 创建知识库（关联到某个部门/项目）
├── 上传文档到知识库
│   ├── 支持格式：PDF / Word(.docx) / Markdown / TXT
│   ├── 文件大小限制：单文件 50MB
│   └── 批量上传（最多 20 个文件）
├── 查看文档列表（含索引状态）
│   ├── PENDING：等待处理
│   ├── PROCESSING：解析/索引中
│   ├── DONE：索引完成，可以查询
│   └── FAILED：处理失败（含错误原因）
├── 删除文档（同时删除对应向量）
└── 重建索引（文档内容更新后触发）
```

### 2.2 问答功能
```plain
问答（Chat）
├── 选择知识库（可选多个）
├── 发送问题（自然语言）
├── 接收流式回答（SSE，边生成边展示）
├── 答案包含来源标注
│   ├── 来源文档名
│   ├── 相关段落原文
│   └── 置信度评分
├── 多轮追问（上下文保持）
└── 会话管理（历史对话列表）
```

### 2.3 权限控制
```plain
权限
├── 知识库归属（属于哪个部门）
├── 访问权限（哪些用户可以查这个知识库）
│   ├── 所有人：公共知识库
│   ├── 指定部门：部门专属
│   └── 指定用户：点对点授权
└── 管理权限（谁能上传/删除/重建索引）
```

## 三、非功能需求（生产级关键）
这部分是很多教程不讲但生产环境必须考虑的。

<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175483251-361d3bd1-93d5-4a18-979e-03a949ed8574.png" width="1111" title="" crop="0,0,1,1" id="ub3c9cc5c" class="ne-image">

### 3.1 性能
| 指标 | 目标 |
| --- | --- |
| 问答首字延迟（TTFT） | ≤ 3 秒（含检索 + Reranker + 首 Token） |
| 文档索引速度 | 10 页 PDF ≤ 30 秒完成索引 |
| 并发问答 | 支持 20 并发提问 |
| 向量检索 P99 延迟 | ≤ 200ms |


### 3.2 准确性
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175505780-261eb10c-597d-4e6a-88ac-eaec1126eab3.png" width="1114" title="" crop="0,0,1,1" id="u9f956797" class="ne-image">

| 指标 | 目标 |
| --- | --- |
| Hit Rate（标准问题集） | ≥ 85% |
| 无答案识别率 | ≥ 90%（知识库里没有时正确回答"没有"） |
| 引用溯源准确率 | ≥ 95%（标注的来源与答案实际来源一致） |


<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175518922-9479706b-245b-4158-b7e2-57ba43b62027.png" width="1111" title="" crop="0,0,1,1" id="ua0242714" class="ne-image">

### 3.3 可靠性
+ 文档解析失败不影响已有索引
+ Reranker 服务超时自动降级（退回向量排序），不影响答案生成
+ Embedding 服务限流时，使用批量重试 + 指数退避
+ 服务重启后，正在处理的索引任务可以恢复（状态机持久化）

### 3.4 成本控制
+ 相同 chunk 不重复向量化（Embedding 缓存）
+ 相同查询 10 分钟内不重复检索（查询缓存）
+ 上下文预算控制：传给模型的 context 不超过 3000 Token

## 四、核心实体梳理
```plain
KnowledgeBase（知识库）
  id, name, description, department, created_by, is_public
  
KbDocument（文档）
  id, kb_id, file_name, file_type, file_size
  minio_path（原始文件路径）
  status（PENDING/PROCESSING/DONE/FAILED）
  error_msg, chunk_count, token_count
  created_at, indexed_at
  
DocChunk（分块）
  id, doc_id, kb_id
  content（原文内容）
  embedding（向量，pgvector）
  chunk_index（在文档中的顺序）
  page_num（来自第几页）
  metadata（JSON：标题、段落类型等）
  
ChatSession（对话会话）
  id, user_id, kb_ids（查询的知识库列表）
  created_at, last_active_at
  
ChatMessage（对话消息）  
  id, session_id, role（USER/ASSISTANT）
  content, sources（JSON：引用来源列表）
  token_count, latency_ms
  created_at
  
KbPermission（权限）
  id, kb_id, subject_type（DEPARTMENT/USER）
  subject_id, permission（READ/WRITE/ADMIN）
  
IndexTask（索引任务）
  id, doc_id, status, retry_count
  started_at, finished_at, error_msg
```

## 五、关键设计决策
### 决策 1：用 PostgreSQL 还是专用向量库？
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175681364-69594c80-e695-4a82-88b7-1e8a3a4c7c0c.png" width="1109" title="" crop="0,0,1,1" id="udefdd6a8" class="ne-image">

**结论：PGVector（PostgreSQL 扩展）**

理由：

+ 向量和文档元数据在同一个库，JOIN 查询很方便（混合检索就需要 JOIN）
+ 专用向量库（Qdrant/Milvus）管理成本高，团队要多维护一个中间件
+ 数据量级在百万以内，PGVector 性能完全够用
+ PGVector 0.7.0 开始支持 HNSW 索引，检索延迟已经很低

何时换专用向量库：**向量数量超过千万、需要多租户向量隔离、对召回延迟有极严苛要求**时再考虑迁移。

### 决策 2：同步索引还是异步索引？
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175688059-9eb22d39-9e81-4a71-aa3b-dad405cfaccd.png" width="1115" title="" crop="0,0,1,1" id="u1e84bf2f" class="ne-image">

**结论：异步索引**

理由：

+ 文档解析（特别是 PDF 的 OCR）可能耗时几十秒
+ 同步处理会让上传接口超时
+ 用户上传后轮询状态即可，体验更好
+ 失败可以重试，任务状态持久化在 DB，服务重启不丢失

### 决策 3：Reranker 用本地模型还是 API？
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175695677-922a82b0-358b-47f9-b288-2899702fa322.png" width="1119" title="" crop="0,0,1,1" id="uc7142a95" class="ne-image">

**结论：API（阿里云 gte-rerank）**

理由：

+ 本地跑 cross-encoder 需要 GPU，成本高
+ gte-rerank API 延迟约 200-500ms，在可接受范围
+ 做好超时熔断，超时降级到向量相似度排序，不影响可用性

### 决策 4：分块用什么策略？
<img src="https://cdn.nlark.com/yuque/0/2026/png/29413969/1776175702213-54a79a93-2434-40d6-8408-0c650b6e5fdb.png" width="1113" title="" crop="0,0,1,1" id="uc0824353" class="ne-image">

**结论：固定窗口 + 语义重叠（Sliding Window）**

+ chunk_size = 512 Token
+ chunk_overlap = 64 Token（相邻块有重叠，避免信息截断）
+ 中文场景按字符数估算 Token（1 个汉字 ≈ 1.5 Token）

高级方案（后续可优化）：

+ 文档结构感知分块（按标题段落分）
+ 语义相似度分块（内容变化时断点）

这个项目先实现固定窗口，再介绍语义分块的差异和参数选择思路。
