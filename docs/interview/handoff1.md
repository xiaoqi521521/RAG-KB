## 项目背景

这是一个将 Spring AI 企业 RAG 知识库项目重构为 Python 的实践项目，目标不是只完成向量检索 Demo，而是覆盖：

- FastAPI + LangChain 的 RAG 服务；
- PDF、Word、Markdown、Text 文档解析、分块和索引；
- PostgreSQL + PGVector，向量检索与 PostgreSQL 全文检索混合召回；
- RRF 粗排、阿里 Reranker 精排和超时降级；
- Token 预算裁剪、引用溯源、防幻觉拒答；
- SSE 流式输出、多轮会话、RAGAS 和自定义检索/生成评估；
- Redis、MinIO、Prometheus、Grafana 以及知识库级权限隔离。

用户的项目主线是：最初 RAG Demo 能运行，但模型答案在参考资料中找不到依据，因此开始补齐企业级 RAG 的检索质量、可解释性、可靠性和观测能力。

## 面试风格与注意事项

- 使用中文，语气友好但要指出错误，不要泛泛表扬。
- 一次只问一个主问题，可以附带需要自然覆盖的观察点，但不要同时抛出多个独立问题。
- 优先基于用户已经准备的面试题提问；只有用户主动声称某个实现或代码现状时，才读取代码核对。
- 不要默认知道用户没有在项目介绍或职责中说出的实现细节；先问职责和设计目标，再追问用户已经提到的实现。
- 要区分“项目介绍中明确的已实现能力”“用户面试中补充的当前实现”“设计取舍”和“后续优化想法”，避免把建议当成现状，也避免把用户追问到未准备的代码细节。
- 不得根据项目技术栈或背景推断某个具体组件承担了某项职责；如果需要追问存储、队列、缓存或故障处理，必须先确认该组件是否用于该功能。
- 只有用户明确说明某项实现后，才能围绕该实现追问异常场景；不能把“可能的设计”写成面试前提。
- 面试问题控制在 1～2 句话内，表达清晰、简洁、开放；每次只围绕一个核心问题，不在题目中罗列观察点、答题步骤、技术方案或标准答案。
- 需要深入时，根据用户回答逐步追问；不要一次性把多个边界问题塞进同一道题。

## 权限问题的最终上下文

本轮曾把参考资料的“部分过滤”与旧 Python 代码的“路由整体拒绝”混淆，已经澄清：

- 参考资料第“四、检索层权限过滤”明确是：`requestedKbIds -> allowedKbIds`，部分无权时过滤后继续检索，全部无权时拒绝。
- 旧 Python 代码在本轮读取时，`rag.py`、`chat.py` 会逐个 `require_read`，任一失败返回 `403`；`HybridRetriever` 假设传入 ID 已授权，仓储只按 `kb_id IN (...)` 和文档状态过滤，并不独立计算权限。
- 用户已经说“此实现差异我已在项目中更新”。下一个会话不要默认旧代码仍是现状；如再次涉及权限，先检查工作树和当前实现，再按当前代码面试。

准备材料中的主线问题和当前专项追问均已完成。后续如继续，可进入模拟二面、项目深挖或针对薄弱点的专项追问。

## 建议技能

- `grilling`：继续进行一次只问一个问题的深度面试，并在回答后追问。
- `handoff`：只有用户再次要求生成交接记录时使用；更新现有交接记录时保留历史结论，不覆盖已面试内容。
