# 企业 RAG 项目面试整体复盘

## 一、面试结论

本轮准备题主线已经完成，覆盖项目架构、索引管道、查询管道、混合检索、Reranker、HyDE、多轮对话、权限、引用、防幻觉、流式输出、评估、成本、部署和项目复盘。

整体表现的优点是：能够解释为什么这样设计，而不只是背技术名词；能够从线上可靠性、成本、权限和评估角度思考 RAG；遇到不确定的问题时愿意承认不知道，再补充合理方向。

当前项目口径应保持一致：

- 项目尚未上线，但索引管道和查询管道已经全流程打通，不是只完成向量检索的 Demo。
- 已覆盖文档上传、加载、分块、Embedding、向量存储、查询改写、混合检索、Reranker、引用溯源、权限、任务重试、降级和监控。
- 当前距离上线主要还缺 VPS、部署和上线前验收。
- 用户表示项目全部由自己负责。

## 二、项目优势

### 1. RAG 主链路完整

能够从文档上传一直讲到最终回答，不会把项目简化成“Embedding 后查向量库”：

```text
文档上传
  -> 解析与结构化处理
  -> 分块
  -> Embedding 与缓存
  -> PGVector 存储
  -> 查询改写 / HyDE
  -> 向量 + 全文混合检索
  -> RRF
  -> Reranker 精排与降级
  -> Token 裁剪
  -> 引用组装
  -> 流式生成
```

### 2. 能解释检索质量问题

对纯向量检索的盲点理解准确：型号、编号、专有名词等精确词不一定能依靠语义相似度稳定命中，因此加入 PostgreSQL 全文检索，再用 RRF 进行排名融合。

Reranker 的定位也比较清楚：RRF 负责低成本扩大召回，Reranker 对问题和候选 chunk 做更精确的相关性判断；外部 Reranker 失败时回退到 RRF，保证可用性。

### 3. 企业级工程意识较强

回答中反复体现了以下工程意识：

- 权限不能只写在 Prompt 中，必须在请求授权和检索数据范围层面控制。
- 索引任务需要持久化状态，失败可重试。
- 新版本索引完成前保留旧版本可查询，避免重建期间出现空库。
- 外部服务需要超时和降级。
- Token 成本需要缓存、预算和监控，而不是上线后再看账单。
- RAG 参数要通过评估集验证，不能只凭感觉调整。

### 4. 技术取舍比较成熟

你能够说明为什么没有继续堆叠 Agent 路由、精细文档 diff 或专用向量数据库：复杂度和维护成本增加，并不一定带来匹配的收益。选择 PGVector 的理由也符合项目规模和现有 PostgreSQL 基础设施。

## 三、已经掌握的关键口径

以下参数和设计在后续面试中要保持一致：

| 项目 | 当前口径 |
| --- | --- |
| `chunk_size` | 512 |
| `overlap` | 64 |
| RRF `k` | 60，后续通过评估验证 |
| Reranker 候选 | RRF 后约 Top20，再精排取 Top5 |
| Reranker 阈值 | 0.5，需通过验证集校准 |
| HyDE 触发 | 初始向量结果置信度不足时触发，当前提到首条分数低于 0.8 |
| 上下文预算 | 约 3000 Token，实际还要给 System Prompt、问题、历史和回答预留空间 |
| Embedding 批量 | 20，低于服务方单批上限 25 |
| Embedding 缓存 | chunk 内容 MD5 + 模型版本前缀 |
| 索引版本 | 新版本先建立，成功后切换，失败保留旧版本 |
| SSE | `status`、`token`、`done`，不可恢复错误再发送 `error` |
| Token 预算 | 80% 预警，100% 后拦截后续新请求，已开始请求继续完成 |
| 预算存储 | Redis，使用 Lua 配合 Redis 命令完成复合原子判断 |

如果实际代码或最新设计已经改变这些口径，应优先更新面试材料，避免代码、职责文档和口头回答互相矛盾。

## 四、需要重点修正的技术表达

### 1. 区分 RAGAS 指标和自定义指标

RAGAS 中你重点提到的生成层指标是：

- Faithfulness
- Answer Relevancy
- Context Recall
- Context Precision

Hit Rate 和 MRR 是你自己构建的检索指标，不要说成“RAGAS 的六个指标”。MRR 也不是“命中排名的均值”，而是每条问题首个相关结果的倒数排名，再对所有问题求平均。

### 2. 不要把生成质量指标绝对化

生成质量确实更接近用户最终体验，但生成指标下降时不能直接断言检索方案一定变差。还要区分：

- 召回内容是否变差；
- Prompt 是否变化；
- 模型或参数是否变化；
- 上下文裁剪是否丢失关键信息；
- 评估结果是否存在统计波动。

更稳妥的说法是：如果最终回答质量经过复核确实回归，就回退；同时定位回归原因，避免只回退而不修复。

### 3. 权限回答要区分两层职责

建议固定表述为：

> 路由层负责认证和请求范围的授权校验；检索层负责对最终 SQL 的知识库、版本、状态和删除标记做硬过滤，确保模型拿不到越权 chunk。

不要把检索层描述成“专门弥补路由层漏洞”，也不要把参考项目的部分过滤逻辑和当前项目实现混在一起。没有先确认代码时，只描述你在面试中明确过的当前设计。

### 4. 不要把查询改写校验说成必选方案

你已经明确选择不增加在线实体校验或额外评估模型，原因是误报、成本和延迟可能不值得。后续应表述为：

> 当前依赖改写模型、用户反馈和离线评估集发现问题；这是一个明确的复杂度取舍，而不是声称语义错误完全不可能发生。

### 5. 不要把 `k=60` 说成自动正确

RRF 的 `k=60` 是初始配置，不等于三路检索自动等权，也不代表所有数据集都最优。更严谨的说法是：先用 60 作为基线，再通过验证集比较不同 `k` 和权重组合。

### 6. 不要把 HyDE 假设答案当真实知识

HyDE 只用于生成检索向量或补充召回，不应直接进入最终回答上下文。最终回答只能使用真实知识库 chunk。触发阈值 0.8 也应说明是当前经验配置，最终要用评估集校准。

### 7. 文档版本方案更接近“版本化重建”，不是真正 diff

你当前描述的是：新版本 chunk 先写入，索引完成后切换当前版本，失败时保留旧版本。这个方案可以称为版本化重建或先增后切换。

Embedding 缓存可以降低内容未变化部分的成本，但如果文档前部变化导致后续 chunk 边界全部变化，缓存命中率可能下降。不要把它直接称为完整的精细增量 diff。

### 8. PGVector 不要只说“慢了就迁移”

更完整的回答顺序是：

1. 先按阶段记录 P50/P95/P99，确认瓶颈确实在向量查询。
2. 用查询计划和数据库指标检查索引是否生效。
3. 根据 HNSW 的查询和构建参数调节延迟、召回率和内存。
4. 检查知识库、版本、状态等过滤条件，以及过滤列索引、分区和 PostgreSQL 资源。
5. 优化仍无法满足目标时，再使用相同数据集和查询集对比 Qdrant 或 Milvus。

容量和 P99 延迟必须附带测试环境、数据量、索引类型和查询条件，不能当作 PGVector 的普遍保证。

### 9. 上线状态要诚实且完整

项目尚未上线并不是问题，但回答不能只停在“还没上线”。建议说明：核心系统已经全流程打通，目前缺少 VPS 和部署；上线前还需要配置管理、密钥和网络安全、备份恢复、并发压测、故障演练、监控告警、回滚流程和验收标准。

## 五、表达层面的主要问题

### 1. 减少口头填充词

回答中“一个是”“然后”“一个呢”“此项目中”出现频率较高。可以改成：

```text
第一个问题是……
我的处理方案是……
结果和取舍是……
```

### 2. 先给结论，再给原因

建议使用以下结构：

```text
结论 -> 背景问题 -> 方案 -> 为什么这样取舍 -> 结果或限制
```

不要一开始连续罗列技术名词，也不要在同一回答里同时展开多个未被追问的边界。

### 3. 少用绝对表达

需要避免：

- “几乎不可能发生”；
- “一定没有影响”；
- “只差 VPS”；
- “Dify 只适合玩”；
- “PGVector 慢就直接迁移”；
- “Redis 命令是原子的，所以整体一定原子”。

建议改为“当前设计没有增加……”“在当前规模和测试条件下……”“这是一个复杂度与收益之间的取舍”。

### 4. 区分事实、当前实现和建议

回答时要明确：

- “当前项目已经实现……”；
- “我的设计取舍是……”；
- “后续可以考虑……”；
- “这里我还没有实现……”；
- “这个指标需要进一步验证……”。

这会显著降低被面试官追问到无法自证的风险。

## 六、建议准备的项目总述

可以将项目浓缩成下面这段：

> 这是一个面向企业内部知识库的 RAG 问答系统，目前尚未上线，但已经打通了文档上传、解析、结构化分块、Embedding、PGVector 存储，以及查询改写、混合检索、RRF、Reranker、上下文裁剪、引用溯源和流式生成的完整链路。项目重点不是单纯接入大模型，而是解决企业场景中的检索质量、权限隔离、可解释性、故障降级和成本监控问题。为此，我使用向量检索结合 PostgreSQL 全文检索，用 Reranker 做精排并在外部服务失败时回退；权限在路由授权和检索 SQL 两层控制；索引任务支持状态追踪、版本切换和失败重试；同时通过 Embedding 缓存、查询缓存、上下文裁剪、Token 埋点和评估流水线控制成本并验证效果。当前主要还缺 VPS、部署和上线前的安全、稳定性与容量验收。

## 七、后续最值得补强的内容

### 优先级高

- 准备一套真实的上线验收标准，而不是只列“安全、可靠、并发”。
- 明确个人负责边界，能够说清哪些代码和设计是自己完成的。
- 把 Hit Rate、MRR、Faithfulness、Context Precision 等指标用一句话准确解释。
- 准备一组实验数据：参数变化、基线、改动后结果和是否上线。
- 统一权限实现口径，明确路由授权、检索硬过滤和多知识库请求的处理方式。

### 优先级中

- 准备 PGVector 的查询延迟定位和迁移判断流程。
- 准备 Redis 预算闸门的完整语义，包括 Lua 原子判断、预算失败和异常处理。
- 准备文档版本切换失败、重试幂等和旧版本清理的完整流程。
- 准备跨文档对比的目标对象、权限边界和上下文组织方式。

## 八、最终评价

你的优势不在于能够罗列最多的 RAG 技术，而在于已经形成了比较清晰的工程判断：先解决检索和数据边界，再补齐降级、成本、评估和监控；能用数据验证参数；知道复杂方案不一定带来更高收益。

当前主要短板是表达有时偏口语化、个别指标定义不够严谨，以及遇到上线准备、性能定位和预算边界时容易先给出过于绝对的判断。把这些口径修正后，项目面试表现会从“技术点丰富”提升到“能独立负责企业 RAG 系统”。
