## 下一会话目标

默认继续使用中文进行项目面试：一次只问一个主问题，用户回答后先点评表达和技术准确性，再决定追问或换题。问题应优先围绕项目材料和已明确的项目事实，不要假设未被用户确认的代码实现。

优先方向可以按以下顺序选择：

1. 模拟二面：围绕系统设计、故障场景、上线验收和个人决策进行综合追问。
2. 薄弱点专项：重点练习上线验收标准、性能定位、指标定义、预算闸门和个人职责边界。
3. 表达训练：让用户先给出 1～2 分钟回答，再压缩成“结论 -> 背景 -> 方案 -> 取舍 -> 结果/限制”的面试话术。

除非用户主动要求，不要立即重复已经跳过的预算扣减时机问题或 HNSW 参数调整后的延迟归因问题。

- 系统已打通文档上传、解析、分块、Embedding、PGVector 存储、查询改写、混合检索、RRF、Reranker、上下文裁剪、引用溯源和流式生成。
- 已具备权限校验、索引任务状态与失败重试、Reranker 失败降级以及 Prometheus/Grafana 监控。

- 路由层负责认证和请求范围授权，检索层负责知识库、版本、状态和删除标记等最终数据范围的硬过滤。没有核对当前代码时，不要把旧代码行为当成当前实现。
- 项目价值应表述为对文档解析、权限、检索、降级、评估和成本治理具有深度定制能力；比较 Dify 或 AnythingLLM 时要承认它们交付快、使用简单，不要使用“只适合玩玩”等绝对表述。

## 已完成内容与薄弱点

`handoff1.md` 已记录完整的问题清单和逐题结论，`整体复盘.md` 已整理关键参数、常见错误表达、项目总述和补强建议。后续只需要遵守以下增量结论：

- RAGAS 的 Faithfulness、Answer Relevancy、Context Recall、Context Precision 属于生成层评估；Hit Rate 和 MRR 是自定义检索指标。不要混称，MRR 要说明按首个相关结果排名倒数求平均。
- RRF 的 `k=60`、Reranker 阈值 `0.5`、HyDE 触发阈值 `0.8` 都是当前配置或基线，应说明最终需要通过验证集校准。
- 上下文预算约为 `3000 Token`，需要给 System Prompt、问题、历史和回答预留空间；不能把“拼接 Top5”说成无条件完整放入上下文。
- HyDE 假设答案只参与生成检索向量，不能进入最终回答上下文；查询改写用于检索，原始问题仍用于最终回答、会话记录和审计语义。
- 文档更新采用版本化重建/先增后切换：新版本失败时旧版本继续可查询，成功后再切换和清理；不要把它描述成已经实现完整的精细 diff。
- PGVector 变慢时先按阶段观察 P95/P99、查询计划、HNSW 参数、过滤条件和 PostgreSQL 资源，优化后仍不达标再比较迁移方案；性能数字必须带测试环境和数据规模。
- Redis 单条命令的原子性不等于多步骤预算逻辑整体原子；当前已明确使用 Lua 将预算判断和累加放在 Redis 侧。预算扣减时机分支已被用户要求跳过，不要主动继续追问。
- 用户的回答容易出现“一个是”“然后”“只差 VPS”等口语化或绝对化表达。点评时帮助其先给结论，并区分“当前已实现”“设计取舍”“后续建议”和“尚未验证”。

## 面试行为约束

- 一次只问一个核心问题，题目控制在 1～2 句话，不要把多个异常场景和标准答案同时塞进问题。
- 不要把建议中的在线改写实体校验、句子级引用匹配、专用向量库迁移或完整增量 diff 说成当前已实现。用户已经明确不采用在线实体校验，改写错误主要通过用户反馈、人工审核和离线评估发现。
- 用户主动说“换个问题”或要求跳过某个分支时，记录为已跳过，不要在下一题马上绕回同一问题。
- 如需核对代码现状，先读取当前工作树；历史材料中曾记录旧 Python 权限实现与参考设计存在差异，用户随后表示已更新，不能直接沿用旧代码结论。
- 用户回答不准确时，先给出具体纠正和一版可用于面试的表达，再继续一个自然追问或切换主题，不要泛泛表扬。

## 建议技能

- `grilling`：继续一次只问一个问题的深度面试，并根据回答逐步追问。
- `handoff`：用户再次要求交接时继续追加新的 handoff 文档，并引用已有复盘材料，避免覆盖历史结论。
- `find-docs`：只有需要核对具体库或组件的当前 API、参数和官方行为时使用，例如 pgvector、Redis、FastAPI 或 LangChain。
